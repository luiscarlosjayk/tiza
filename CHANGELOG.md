## [Unreleased]

### Changed
- Presentation with moves within the frame budget. Every stable layout (presentation mode, `:layout stable`, `render_text`, each frame of `--all-steps`, the GIF and the cast) computed the take's geometry again, a clone and a projection of the document for every step where something changes; the instance now keeps it until the document changes (a step change keeps it too, unless the step starts typing), and the exports compute it once before their loop. On a 2,000-line document with 200 annotations and 10 moves over 20 steps, a presentation frame went from 46 ms to 4.8 ms (release, Luis's Mac); the output is the same byte for byte (the exports of 45 documents, 576 files: every step as txt, ansi and svg, md, GIF and cast; the instance's frames and `render.text` at every step, against a layout that computes the geometry). `scene.patch` with a `step` now shows that step's code, as a step change does (it kept the code of the step before). `status` builds its warnings from what the last frame laid out instead of laying the document out again, and a read-only request (`status`, `render.text`, `code.get`…) no longer redraws the screen unless it changed something. Highlighting uses at most 4 threads (was 8): each keeps a regex cache for the whole session. `scripts/bench.sh` has the new `present_moves_frame` scenario.
- Release and crates.io: CI and the release workflow install the toolchain `rust-toolchain.toml` pins (Rust 1.99.1, the only place the version is written) with `rustup toolchain install`, and the release build adds its target to that toolchain with `rustup target add`, instead of `dtolnay/rust-toolchain@stable`, which put the target on a `stable` toolchain the build did not use (the cross-compiled `x86_64-apple-darwin` had no standard library); `cargo-deny-action` already installed the pinned toolchain itself. crates.io is published by hand (Luis, 2026-10-22: no workflow publishes and no secret is needed): the README («Installation», «Releases (maintainers)») lists the steps — `cargo publish --workspace --dry-run --locked` first, then `cargo publish --locked -p` for `tiza-core`, `tiza-export`, `tiza-tui`, `tiza-mcp` and `tiza`, in that order, and how to check the index before the next one —, and `scripts/release-local.sh` stays the fallback for the archives. The crates.io page of `tiza` gets a README of its own (`crates/tiza-cli/README.md`, absolute links and image, since the repository's README links relative paths), `homepage`, `documentation` (the README on GitHub), keywords and categories; `tiza-core`, `tiza-tui`, `tiza-mcp` and `tiza-export` say in their description, the first line of their docs and a short README that they are internal crates, published only so that `cargo install tiza` works, with no stable API. Not run on GitHub yet: the workflows were checked locally (YAML and structure, by the QA tests), and `cargo publish --workspace --dry-run` passes with the version set to 0.1.0 (at 0.0.1, already on crates.io, it builds against the published crates).
- A parameter of the wrong type is named in the error again (t-189): `annotation.add {"line": "three"}` answers `invalid type: string "three", expected u32` over the socket and the MCP, where since t-167 it said `string «…»`, which hid what the agent sent. Long values are cut at 40 characters with `…` (also when a `.tiza` is loaded), and a value with a newline or a control character is shown escaped (`\n`, `\u{1b}`), never raw. A value outside a fixed set (a color, a border, a type, an op…) is still never repeated: the error lists the valid names.
- MCP discovery for clients that defer tools (t-162): Claude Code's tool search loads only tool names and the server `instructions` at the start, so the instructions are now a description to search by (977 characters): the positioning sentence, when to use Tiza (explain code to a person or another agent, live or recorded, step by step: a code walkthrough, tutorial, screencast or presentation), the words people use (box, arrow, highlight, note, callout, mark, step, type code / move, link another file, export PNG/GIF), the flow in two lines, three facts the t-161 trials tripped on (annotating at step N creates step N and `goto_step` goes no further than the last; a `find_end` of `}` takes the first brace after `find_start`, often an inner block's) and the `tiza://` resources. `status`, `get_code`, `render_text` and `add_box` carry `_meta["anthropic/alwaysLoad"]: true` (the key Claude Code documents for tools that load upfront), so the first call needs no search; a client that does not know the key loads them as before. No tool is renamed and no parameter or behaviour changes.
- Two or more labels on one line are drawn under that line (t-172, Luis's option b): with the side margin (wide terminals), a line that carries several labels at the current step — a highlight's or a mark's label, notes, the label of an arrow ending there, a margin callout with no room for its block (drawn as its words), any mix — draws all of them on the under-line rows the narrow layout already uses (`· the key`, `┆ DB connection string`, `─▶ label` for an arrow), in the narrow layout's order, and the code below moves down; every other line keeps its label in the margin. ### Added
- Live pointer (t-030): `f` toggles it on the cursor line, or on the lines of a `v`/`V` selection — those lines are drawn as they are and the rest of the code is dimmed with the spotlight's dimming, over any `:focus` or spotlight; annotations stay as they are. It follows every motion (`j`/`k`, `g`/`G`, `J`/`K`, the mouse with `--mouse`), works in presentation mode (`P`, then `f` and `j`/`k`; the cursor stays hidden), stays on its line across `n`/`p` (carried through the step's moves; off when the line is gone) and `f` again or `Esc` turns it off (the status bar says `POINTER` while it is on). It is a toggle, not a key held down: knowing when a key is released needs the kitty keyboard protocol, which Tiza does not enable (t-034). It is never part of the document — no annotation, no revision, no undo entry, no autosave — and no export draws it (`:export`, `tiza render` PNG/SVG/GIF/MP4/.cast/.tape/txt/ansi/md, `export_image`, `render.text`). Agents point with the same pointer: socket `pointer.set` (`{line}`, `{line, find}`, `{find}`, `{from, to}`) and `pointer.clear`, MCP `point_at` and `clear_pointer` (30 tools), and `status` carries `pointer` (`{line, to, by}` or `null`); the last one wins. Under `:supervise` they wait for the presenter's `y`/`n` like `focus.set`.
- Demo scenarios (t-046): `docs/demos/scenarios.md` catalogues twelve ways to use Tiza with an agent, each with its audience, setup, script, what is seen, the features it uses and recording notes — a codebase tour across a few files, one agent explaining a change to another for review, a walkthrough one agent leaves for the next, a before/after change with `code.patch`, a bug traced across files, a config file with demo values, live coding with follow mode, a supervised session, a one-concept lesson, two implementations compared, an answer in an issue as an annotated frame, and a looping hands-free screen — none of them waiting on a feature: every scenario works on a copy of its sample (`cp -r examples/tally /tmp/tally`) and keeps the `.tiza` sidecar the TUI autosaves as its result, one file is on screen per step (each explained at its own step with `code.link`), the agents sign their own labels and notes, the agent writes `code.patch` moves from a `git diff` itself, and the config scenario works on a throwaway file with demo values. It ends with the one planned change that touches them: exporting a live multi-file instance (t-166; until then the scripts render the sidecar). The tour is worked out in full: `examples/tally/` is a four-file Rust CLI (a tiny `wc`, it builds with `cargo run`), `examples/tally-tour.tiza` the five-step take over it (four `code.link` moves, a `select`, named steps, 16 annotations; `tiza check --width 130` clean), and the document gives the eight prompts that build it; `qa/tests/t-046.rs` replays their MCP calls on a live instance and checks every step of the sidecar it autosaves draws exactly as the shipped file. Linked from the README («For agents») and `examples/README.md`.

The rules are the layout's (`Document::why_hidden`). The MCP `add_box`, `add_arrow`, `add_note`, `highlight`, `add_mark`, `add_callout`, `add_spotlight` and `update_annotation` start their result with one sentence: `a17 added at step 1; not visible now: the view is at step 0 and it appears at step 1 (next_step shows it).` In supervised mode the reply is computed when the presenter accepts, so `shown_step`/`visible` describe that moment. `annotation.delete` is unchanged. Schema (`schema/api.schema.json`, result `AnnotationMutated`) and agent guide («Is it on screen?») updated. The presenter is told too (t-155 AC2, Luis's call on the rework): when a socket/MCP call — never a key or a `:` command — adds or changes an annotation the view does not show, the status bar says so with the summary of the `:` command that would make it, ` by agent` and the t-132 tail: `a17: box 3-5 added by agent (step 1, press n)`, `a4: note L13 updated by agent (step 3, :step 3 shows it)`, and, when a `code.link` shows another file, `a9: note L17 added by agent (src/queue.rs, not shown at step 2)` (other reasons in words: `(not shown: its lines are outside the code shown at step 5 (17-23))`). In presentation mode nothing is drawn (the presentation line is for what the presenter types, t-107); the notices wait and reach the bar when presentation mode ends (`P`, `:present` or now also Esc, which goes through the same path and so also opens the pending proposals' list, as `P` does), without those the presenter has reached meanwhile. - Preflight: `tiza check FILE` (t-101) loads a `.tiza` (or a source file's sidecar, or `-`) the way the TUI does but lists every problem instead of stopping at the first, each naming the annotation or move (`move #3`), the step, the linked file and the line. Errors (exit 1): a schema violation (with the `.tiza` line), code or a linked file that cannot be read (one error per file, naming the moves that link it; its moves and annotations are not checked), a duplicate id, an unknown id (spotlight `ids`, `rebind`), an anchor out of the code, a marker that matches nothing, a move whose target matches nothing or more than once at its step (a broken move is replaced by one that does nothing, so the later ones are still checked on the code they would see), a `rebind` that does not match exactly once. Warnings (exit 0; `--strict` fails on them): an annotation hidden as `(unanchored)` (with its steps), a label clipped with «…» or left out for lack of room at the width of the take (100 as `render`, or `--width N`; named with its first step, id and full text), a step with nothing new, a named step past the last one. It ends with the narrowest width from which no label is clipped at any step with the stable geometry of a take (`examples/ownership.rs.tiza`: two clipped labels at 100, clean from 108). `--json` prints the same report; the MCP gets a `check` tool with the same JSON on the live document (a tool and not a field of `status`: `status` is called often and stays cheap, and `check` takes a `width`). It writes nothing. The layout now records the labels it clips (`Layout::clipped_labels`).
- `tiza check` rework (t-101, QA 2): the MCP `check` tool now asks the instance (new read-only socket method `check`, the same report as `tiza check --json`), which checks the document it holds — real code, linked files and unsaved changes — instead of the copy of `scene.get`. A marker that matches more than once is a warning naming its lines (`start marker «open(» matches 2 times (L3, L6): the range takes the first one (L3)…`). A clipped label says the step it names is the first (`at width 100, first at step 3, then at steps 5-7`); a message about a linked file names it (`src/queue.rs spans 1 to 3`, not `the document spans…`). - Named steps, auto-advance and loop (t-099, [ADR 0007](docs/adr/0007-moves-y-pasos-con-nombre.md) §4): `"steps": [{"step": 3, "id": "borrow", "title": "Shared borrow", "auto_advance_ms": 3000}]` in the `.tiza` (each entry bound by its explicit `step`, sparse, saved sorted; ids unique, one word, not all digits and not starting with `-` — duplicates, digit-only ids and `-` ids fail to load, and `scene.patch` refuses them with `invalid_argument`; an entry past the last step, or a key an entry has that Tiza does not know such as the dropped `timer_min`, is kept and warned about in `status.warnings`, on stderr by `render` and by `tiza check`, never dropped) and `"loop": true`. ### Added
- Moves (t-098, ADR 0007): a `.codedraw` may carry `moves`, `code.patch` entries that insert, replace or delete whole lines when the presenter reaches `at_step` and are reverted when going back; the document is recomputed from the step-0 code every time (no diff of diffs). Targets are matched on the code as shown at that step and must match exactly once (`after`/`before`/`position` for inserts, `find`/`find_start`+`find_end`/`position` for replace and delete); load-time and `move.add` errors name the move. `typing: line|char` types the content in place in the TUI (`speed_ms` per unit; blank placeholder lines keep the layout steady; any key finishes it; the step's annotations appear when it ends). Annotations are authored against the code at their own step (`annotation.add` validates on that step's code) and shifted deterministically through later patches by the patch's own line map — never by a text search; one that loses every line is hidden and listed as `(unanchored)` in `scene.list`/`:list`, unless the move's `rebind` says where it goes. A `replace` keeps line-level annotations (note, box, callout, spotlight) on the same-offset line but unanchors column anchors (highlight, mark, arrow ends) unless `rebind`; `occurrence: N` (1-based over the whole code at that step; `end_occurrence` for `find_end`) picks a match on every text target and on `rebind` finds, which are validated when the move is added. Socket `move.add`/`move.delete`/`move.list`, MCP `add_move`/`delete_move`/`list_moves`, `scene.get` carries `moves` with the step-0 code embedded; the saved file and `:embed` always keep the step-0 code; `render --step N`, `.cast` and `.tape` apply the moves instantly; paste and follow are refused while a move is applied. Example `examples/ownership-moves.rs.codedraw`; undo covers moves and typing.
- Range anchors by two text markers (t-097): boxes, callouts and spotlights accept `find_start`/`find_end` on the socket and in the MCP tools, and `:box @'// begin'..@'// end' label` (also `:callout`, `:spot`) in the TUI; resolved at creation (first start anywhere, first end at or after it, same line allowed) and stored as lines plus `markers: {start, end}` on the annotation (shown in `scene.list`, dropped when the annotation is moved by lines). Missing markers fail with `text_not_found` naming them; an end that only appears before the start is `invalid_argument`.
- Mouse support, opt-in (t-033): `--mouse` / `:mouse on|off`. Click moves the cursor to the line and grapheme (tabs and wide glyphs by display width; virtual rows snap to the code line above), drag selects a span or a line range and leaves the selection open for the usual actions, the wheel scrolls three rows; ignored while an overlay or the command line is open, and in presentation mode (`P`), where the cursor and the selection are hidden — the capture stays on, so back in normal mode the mouse works again. Off by default so the terminal keeps its native selection (README explains Shift/Option-drag, Zed's Cmd+click and tmux).
- Legibility check (t-072): `scripts/legibility.py DOC --step N --theme dark|light` renders, scales to 1920×1080, round-trips through H.264 at a YouTube-like bitrate and measures the contrast each text color keeps (stroke cores vs background); exit 1 under 4.5:1. The ownership example passes in both themes (worst ≈ 4.9 dark, ≈ 5.0 light). CI job `legibility` runs it and uploads the report; `qa/tests/t-072.rs` also checks every theme role before compression.
- Brand typography in exports (t-068): notes, labels, mark legends and under-line labels can be set in *Tiza Serif* (first shipped as *CodeDraw Serif*, renamed with the project), a Latin subset of Libron (OFL, renamed per the license) embedded in the binary and in the SVG (four faces, ~340 KB); code, numbers, boxes and titles stay in JetBrains Mono. New `CellStyle.prose` flag (ignored by the terminal). After the owner's review the serif became opt-in (see Changed), and t-134 later took it out of the binary (see Removed); it lives on as brand material in [`docs/brand/fonts/`](docs/brand/fonts/README.md).
- Recordings from the steps (t-051): `codedraw render FILE --out x.cast` writes an asciicast v3 (header with the document title, one marker + one frame per step from step 0, `--interval` seconds apart, theme background, CRLF, no scrolling) and `--out x.tape` a VHS tape that drives the real TUI through the steps (`vhs x.tape` → `x.gif`). `--format cast|tape`, `--skip-zero`, `--title`; the live instance can be recorded too.

Mutating requests from agents are parked as proposals; the review overlay (`:review`, `y`/`n`/`a`/`d`, Esc) and the `⏸ N to review` chip show them; the agent's call returns the normal result on `y`, error `rejected` on `n`, on `:supervise off` or after 60 s undecided. - Highlight and mark emphases (t-096): `emphasis` = `fill` (tint, default), `underline` (a virtual row with ▔ under the span), `brackets` (⌈ ⌉ beside the span; a glued side falls back to ⌊ ⌋ on the row below so code is never covered) or `strike` (combining stroke per grapheme, also in SVG/PNG). `:hl … emphasis=…` (`style=` as a synonym on `:hl`), `:mark … emphasis=…`, `:set ID emphasis=…`, socket field on `annotation.add/update`, MCP `highlight` / `add_mark` / `update_annotation`. - Follow mode (`--follow`, `:follow on|off`): the TUI watches the source file's folder (tmp + rename saves included) and reloads the code ~120 ms after the last write, re-anchoring annotations by text like a paste (a box or callout keeps its height when one edge line is edited; the ones whose text is gone are dropped and `u` undoes the reload). Re-anchoring (shared with paste) now runs a line diff and matches lines in order, then the same occurrence of the span inside the line: a note on the second `}` or the second `fn new()` stays on its own copy, a deleted copy drops its annotation instead of jumping to another one, and a moved block is followed when its line is unique and within `reanchor::MAX_DISTANCE` (50 lines). From the QA rounds in real Zed: box, callout and spotlight follow one rule — when an edge line leaves with a moved block the range keeps its height from the edge that stayed (never stretching after the one that left, never dropping a spotlight where a box is kept), and a block cut and pasted elsewhere takes its callout with it (the line diff prefers contiguous runs, so a moved block is one deletion plus one insertion); a line replaced in place keeps its note (a span on it still needs its text); a formatter split or join (rustfmt `Self { items: Vec::new() }` ↔ three lines) carries a span to the one new line that holds its text; and a reload that touches no annotation leaves no undo step, so after an editor undo one `u` reaches the reload that dropped something. Status line `⟳ following · last HH:MM:SSZ`; removed file → waiting; empty intermediate writes deferred; identical content, non-UTF-8 and the sidecar autosave never reload. - Paste re-anchors annotations by the text they pointed at (same line first, then anywhere); the ones whose text is gone are dropped with a message and `u` restores them. Pasting while typing a `:` command appends to the command; an empty paste is refused.
- Help and list overlays scroll (`j`/`k`, PgUp/PgDn, `g`/`G`) and show how much is left; `:`, `?` and `L` work while a selection is active; `Tab` at step 0 explains that nothing is visible.
- Arrow styles, per annotation like color: `stroke` (solid, dashed, dotted, thick, double), `route` (rounded, sharp) and `heads` at both ends (none, arrow, dot, bar, open; none+none is a plain connector). `:arrow … stroke=dashed heads=dot,bar route=sharp`, new `:set ID key=value…` (also `e` on a selected annotation), socket fields on `annotation.add/update`, MCP `add_arrow` / `update_annotation` with `stroke`, `route`, `head_start`, `head_end`. Crossings now choose the junction from the two strokes (┼ ┿ ╂ ╋ ╪ ╫ ╬). The ownership example draws the shared borrow dashed and the mutable borrow thick.
- Viewport warnings: a ⚠ badge in the status line when the terminal is smaller than 100×30 (saying when labels go under the lines) or when the widest code line is clipped; `status` returns the same texts in `warnings`. Narrow status bars drop the theme/file/cursor segments before cutting the warning.
- `qa/`: one integration-test crate per board ticket (`qa/tests/t-XXX.rs`, fixtures in `qa/fixtures/`), with a headless `Live` instance (real `App` + socket) to drive keys, commands and the API without a terminal.
- SVG and PNG export (`codedraw render FILE --out x.svg|x.png`, `--step`, `--theme`, `--scale`, `--font-size`, `--margin`, `--radius`, `--no-embed-fonts`, `--system-fonts`). Without FILE it exports what the live instance is showing. MCP tool `export_image`. Fonts (JetBrains Mono + a symbols fallback) are embedded in the binary and in the SVG, so the image looks the same everywhere. New crate `codedraw-export`.
- `scene.get` sends the code embedded, so clients in another directory can render the live document.
- `update_annotation` (MCP) and `annotation.update` (socket, `move`) can move an annotation keeping its type, kind, style and label: `at` for highlights/marks/notes, `from`/`to` for arrows, `from_line`/`to_line` for boxes, callouts, spotlights and notes. Fields that do not apply to the type fail with `invalid_argument`; the MCP tool rejects unknown fields instead of ignoring them.
- `callout` annotation: a bordered multi-line paragraph explaining a range of lines, with optional title, `placement` (`margin`, `below`, `auto`) and `width`. `:callout A[-B] [@below|@margin|@auto] [title="…"] text`, `C` on a selection, `annotation.add` with `type: callout`, MCP `add_callout`. In the margin it reserves its rows and the neighbouring labels are drawn beside it instead of being pushed down; below, boxes extend around it. The ownership example closes with one (step 7).
- Default padding of one column at the left and right edges when the document sets none (`:pad 0 0` removes it, `:pad default` restores the default).
- `Tab`/`Shift-Tab` select an annotation in reading order; on it, `Enter` edits the label, `x` deletes, `c` changes the color, `+`/`-` move it between steps.
- Command line: `Tab` completes commands, mark kinds, annotation ids and themes; `↑`/`↓` browse the history.
- Padding around the drawing: `--padding V[,H]` when opening and `:pad V [H]` live; stored in the document (`padding: [v, h]`).
- Keyboard selection, vim style: column cursor with `h`/`l`/`w`/`b`/`e`/`0`/`$`, `v`/`V`/`i` selections, and selection actions `h` (highlight), `m` (mark, command line pre-filled), `n` (note), `b` (box), `a` (arrow in two selections), `s` (spotlight). Explicit anchors `L@S..E` and `L@C`. The annotation list moves to `L`.
- Generic, language-agnostic mark kinds (info, warn, error, ok, question, important, read, write, move, new, drop, scope, flow, todo) replacing the Rust-only set; Rust names remain as aliases. Custom styles in two modes: inline per annotation (`style: {glyph, legend, color}`, emoji allowed) and reusable document `styles` (`:style NAME …`, MCP `define_style`, `list_kinds`). `:mark 🔥 L:text legend` creates a one-off mark.
- `spotlight` annotation: a step that directs attention by dimming the code outside a range and/or the annotations outside a group (`:spot`, `:until`, `add_spotlight`, `annotation.add` with `type: spotlight`). The ownership example interleaves two.
- `code` as an object `{"file", "lines"}` with absolute paths or paths relative to the `.codedraw`; sidecars reference the source by default. `:embed` and `:link`.
- Step 0 = code only: `p` from step 1, `:step 0`, `--step 0` or `set_step 0` show the code without annotations. The ownership example starts that way.
- Clear annotations at once: `:clear [N|.]`, the `scene.clear` method and the `clear_annotations` MCP tool; reversible with `u`.
- Color per annotation (`color`: palette name or `#rrggbb`) in the model, `:color ID …`, API and MCP. Arrows without a color rotate through a palette so they can be told apart; the ownership example uses one color per value.
