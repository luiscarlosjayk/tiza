### Added
- Live pointer (t-030): `f` toggles it on the cursor line, or on the lines of a `v`/`V` selection — those lines are drawn as they are and the rest of the code is dimmed with the spotlight's dimming, over any `:focus` or spotlight; annotations stay as they are. It follows every motion (`j`/`k`, `g`/`G`, `J`/`K`, the mouse with `--mouse`), works in presentation mode (`P`, then `f` and `j`/`k`; the cursor stays hidden), stays on its line across `n`/`p` (carried through the step's moves; off when the line is gone) and `f` again or `Esc` turns it off (the status bar says `POINTER` while it is on). It is a toggle, not a key held down: knowing when a key is released needs the kitty keyboard protocol, which Tiza does not enable (t-034). It is never part of the document — no annotation, no revision, no undo entry, no autosave — and no export draws it (`:export`, `tiza render` PNG/SVG/GIF/MP4/.cast/.tape/txt/ansi/md, `export_image`, `render.text`). Agents point with the same pointer: socket `pointer.set` (`{line}`, `{line, find}`, `{find}`, `{from, to}`) and `pointer.clear`, MCP `point_at` and `clear_pointer` (30 tools), and `status` carries `pointer` (`{line, to, by}` or `null`); the last one wins. Under `:supervise` they wait for the presenter's `y`/`n` like `focus.set`.
- Demo scenarios (t-046): `docs/demos/scenarios.md` catalogues twelve ways to use Tiza with an agent, each with its audience, setup, script, what is seen, the features it uses and recording notes — a codebase tour across a few files, one agent explaining a change to another for review, a walkthrough one agent leaves for the next, a before/after change with `code.patch`, a bug traced across files, a config file with demo values, live coding with follow mode, a supervised session, a one-concept lesson, two implementations compared, an answer in an issue as an annotated frame, and a looping hands-free screen — none of them waiting on a feature: every scenario works on a copy of its sample (`cp -r examples/tally /tmp/tally`) and keeps the `.tiza` sidecar the TUI autosaves as its result, one file is on screen per step (each explained at its own step with `code.link`), the agents sign their own labels and notes, the agent writes `code.patch` moves from a `git diff` itself, and the config scenario works on a throwaway file with demo values. It ends with the one planned change that touches them: exporting a live multi-file instance (t-166; until then the scripts render the sidecar). The tour is worked out in full: `examples/tally/` is a four-file Rust CLI (a tiny `wc`, it builds with `cargo run`), `examples/tally-tour.tiza` the five-step take over it (four `code.link` moves, a `select`, named steps, 16 annotations; `tiza check --width 130` clean), and the document gives the eight prompts that build it; `qa/tests/t-046.rs` replays their MCP calls on a live instance and checks every step of the sidecar it autosaves draws exactly as the shipped file. Linked from the README («For agents») and `examples/README.md`.
- `annotation.add` and `annotation.update` say whether the annotation is on screen (t-155): the reply keeps `id` and `revision` and adds `step` (the annotation's step; `step_title` too when it is named, t-099), `shown_step` (the step the view shows when the change is applied) and `visible`, plus `hidden` with the reason in words when it is not drawn — `it appears at step 1`, `its file src/queue.rs is not shown at step 2 (main.rs is)` (t-105's views), `its lines are outside the code shown at step 2 (10-36)`, `it lost its anchor at step 2 (unanchored: …)`, `a spotlight shows only at its step 1`. The rules are the layout's (`Document::why_hidden`). The MCP `add_box`, `add_arrow`, `add_note`, `highlight`, `add_mark`, `add_callout`, `add_spotlight` and `update_annotation` start their result with one sentence: `a17 added at step 1; not visible now: the view is at step 0 and it appears at step 1 (next_step shows it).` In supervised mode the reply is computed when the presenter accepts, so `shown_step`/`visible` describe that moment. `annotation.delete` is unchanged. Schema (`schema/api.schema.json`, result `AnnotationMutated`) and agent guide («Is it on screen?») updated. The presenter is told too (t-155 AC2, Luis's call on the rework): when a socket/MCP call — never a key or a `:` command — adds or changes an annotation the view does not show, the status bar says so with the summary of the `:` command that would make it, ` by agent` and the t-132 tail: `a17: box 3-5 added by agent (step 1, press n)`, `a4: note L13 updated by agent (step 3, :step 3 shows it)`, and, when a `code.link` shows another file, `a9: note L17 added by agent (src/queue.rs, not shown at step 2)` (other reasons in words: `(not shown: its lines are outside the code shown at step 5 (17-23))`). Agent changes within 1 s of the last one share one message, counted again against the view: `3 agent annotations not shown (step 1, press n)`. In supervised mode there is no new message: the acceptance gets the tail (`accepted p1: add box L3-5 (step 1, press n)`). In presentation mode nothing is drawn (the presentation line is for what the presenter types, t-107); the notices wait and reach the bar when presentation mode ends (`P`, `:present` or now also Esc, which goes through the same path and so also opens the pending proposals' list, as `P` does), without those the presenter has reached meanwhile. A visible change, an error the request raised itself (a failed save) keeps the bar as it was; the bar and the presentation line keep the file tail when they cut the message, like the step tail. `Document::why_hidden` is now the text of `Document::hidden_reason` (enum `Hidden`), which the bar uses too.
- Preflight: `tiza check FILE` (t-101) loads a `.tiza` (or a source file's sidecar, or `-`) the way the TUI does but lists every problem instead of stopping at the first, each naming the annotation or move (`move #3`), the step, the linked file and the line. Errors (exit 1): a schema violation (with the `.tiza` line), code or a linked file that cannot be read (one error per file, naming the moves that link it; its moves and annotations are not checked), a duplicate id, an unknown id (spotlight `ids`, `rebind`), an anchor out of the code, a marker that matches nothing, a move whose target matches nothing or more than once at its step (a broken move is replaced by one that does nothing, so the later ones are still checked on the code they would see), a `rebind` that does not match exactly once. Warnings (exit 0; `--strict` fails on them): an annotation hidden as `(unanchored)` (with its steps), a label clipped with «…» or left out for lack of room at the width of the take (100 as `render`, or `--width N`; named with its first step, id and full text), a step with nothing new, a named step past the last one. It ends with the narrowest width from which no label is clipped at any step with the stable geometry of a take (`examples/ownership.rs.tiza`: two clipped labels at 100, clean from 108). `--json` prints the same report; the MCP gets a `check` tool with the same JSON on the live document (a tool and not a field of `status`: `status` is called often and stays cheap, and `check` takes a `width`). It writes nothing. The layout now records the labels it clips (`Layout::clipped_labels`).
- `tiza check` rework (t-101, QA 2): the MCP `check` tool now asks the instance (new read-only socket method `check`, the same report as `tiza check --json`), which checks the document it holds — real code, linked files and unsaved changes — instead of the copy of `scene.get`. A marker that matches more than once is a warning naming its lines (`start marker «open(» matches 2 times (L3, L6): the range takes the first one (L3)…`). A clipped label says the step it names is the first (`at width 100, first at step 3, then at steps 5-7`); a message about a linked file names it (`src/queue.rs spans 1 to 3`, not `the document spans…`). The closing line reads `no label is clipped at 108 or wider (…)`, and when the width asked for is clean but narrower it says which narrower widths are clean too (`79-93 are clean too (notes go under the lines below 94 columns)`, JSON `narrower`). `render --all-steps` honours `--skip-zero` (from step 1; refused on a document with only step 0), removes the `step-NN` files of its format an earlier run left beyond the last step and names the ones of other formats it leaves; only names this run writes count (`step-` + the same number of digits, the last step's and at least two, + `.` + the format, lowercase, a regular file), so `step-1.png`, `STEP-05.PNG`, `step-05.png.bak` or a `step-0123.png` next to a 7-step take are neither removed nor named, a directory or symlink named like a step is left and named, a leftover that cannot be removed is a warning (exit code unchanged), and a long list ends with «and N more» (second rework, QA 2), and says `wrote 1 file`. `check --help` no longer lists `--socket`/`--session` (still accepted).
- `tiza render FILE --all-steps --out DIR/` (t-101): `step-00.png` … `step-NN.png` (or `--format svg|txt|ansi|md`), step 0 included and one image for a document with no annotations, every image padded to the same pixel size; `--out -` and the recording formats are refused.
- Named steps, auto-advance and loop (t-099, [ADR 0007](docs/adr/0007-moves-y-pasos-con-nombre.md) §4): `"steps": [{"step": 3, "id": "borrow", "title": "Shared borrow", "auto_advance_ms": 3000}]` in the `.tiza` (each entry bound by its explicit `step`, sparse, saved sorted; ids unique, one word, not all digits and not starting with `-` — duplicates, digit-only ids and `-` ids fail to load, and `scene.patch` refuses them with `invalid_argument`; an entry past the last step, or a key an entry has that Tiza does not know such as the dropped `timer_min`, is kept and warned about in `status.warnings`, on stderr by `render` and by `tiza check`, never dropped) and `"loop": true`. The status line shows `step 3/7 · Shared borrow`, `status` adds `step_id`, `step_title`, `step_label`, `auto_advance_ms` and `loop`, MCP `list_annotations` starts with that line. New socket method `step.goto {id}` (an id or a step number; unknown → `not_found`), MCP tool `goto_step` (an id or a number, `{"id": 4}` or `"4"`; anything else, such as `-1`, `4.5` or `null`, is `invalid_argument` naming the valid range), `:goto ID`, and the CLI `tiza next`, `tiza prev`, `tiza goto ID` (session socket or `--socket`; no instance → exit 1): a goto lands as walking from step 0 would (moves, views recomputed; a typed step complete). `auto_advance_ms` moves the TUI on by itself once the step is ready (typing and `wait` finished; a key meanwhile only finishes the typing; deferred while `:`, a `v`/`V` selection or an overlay is open); `loop` makes `n` past the last step go to step 0. `scene.patch` takes `steps` and `loop`; undo covers them. The native GIF and MP4/WebM hold a step with `auto_advance_ms` for exactly that long (after its typed frames) and `--interval` for the rest — Luis's decision of 2026-10-18 — and the GIF summary names those steps; a `.tape` sends no `n` after such a step (the real TUI advances by itself). `docs/zed.md` gets `next`/`prev`/`goto` tasks (not yet run in Zed). No presenter notes, no timer.
- Terminal size matrix with Herdr (t-071): `scripts/herdr-matrix.sh` runs the ownership example at step 7 in terminals of 80×24, 120×40, 75×50, 60×30 and the largest the window allows (presented, plus two normal-mode runs with the status bar), sizes being what Tiza sees: it measures Herdr's pane frame first (the `pane layout` rect minus `tiza api status` on a probe pane, 3×2 on Herdr 0.9.5) and splits each pane at target + frame with the ratio read off `herdr pane layout` (fixing the last cell by growing the pane or its neighbour, since Herdr never shrinks a pane at the right with `resize right`, and resizing by the difference a pane whose frame differs). It works in a tab of its own (`herdr tab create … --label tiza-matrix`, closed at the end, also on errors and Ctrl-C; `--base PANE` splits one of your panes instead), saves what Herdr's terminal emulator shows as `qa/herdr/<case>-<cols>x<rows>.txt` named by Tiza's size (Herdr's rect printed next to it), and with `--check` diffs against the committed snapshots (`--update` rewrites them). - Presentation mode shows the command line (t-107): pressing `:` while presenting draws the `:` line on the last row — over the padding or the last code line, the same text, completions and cursor as on the status bar — and Enter or Esc hides it; the command's result (confirmation or error) stays there for 2 s (`PRESENT_MESSAGE_TTL`) or until the next key, so a typo like `:foo` no longer fails in silence. Nothing else of the status bar appears; with the line hidden the frame is unchanged (snapshot in `qa/tests/t-107.rs`), and `render`, `--out` exports and the `.tape` do not draw the TUI frame at all.
- Moves between files (t-105, [ADR 0007](docs/adr/0007-moves-y-pasos-con-nombre.md) §3f rewritten): `code.link {file, lines?}` shows another file from its step on, and each file is a view with **its own annotations** — an annotation carries an optional `file` (absent = the document's own file), filled in from the file shown at its step when added without one; lines are real file line numbers; `lines` is only a window (a note outside it is kept, not drawn; the same file with another window is the same view); linking the main file again brings its annotations back untouched, nothing goes `(unanchored)` because of a link. `:link path[:A-B]` at a step ≥ 1 records the move (`:ref`, or `:link` at step 0, is the one-shot file reference); `:list`/`scene.list` end an annotation of a linked file with `(file)`; the bar shows `↪ file:A-B`; `code.get`, `status` and `move.list` report the view (`file`, `view`, `first_line`, `last_line`); a `code.patch` edits the file shown at its step; `:embed` and `scene.get` store every linked file under `views` so the demo stays one portable `.tiza`; a link to a file that cannot be read fails to load naming the move and the path. With it, `cursor {line, col?}`, `select {from, to}` (each end a `find` matching exactly once or `line`/`col`; drawn in the TUI, `render --step N` and every export) and `wait {ms}` (the TUI, the GIF and the `.tape` pause; a `.cast` holds the frame; a still render ignores it). Socket `move.add` and MCP `add_move` (`action`) accept the four; `examples/stack-and-queue.tiza` links a stack and a queue back and forth.

### Added
- Moves (t-098, ADR 0007): a `.codedraw` may carry `moves`, `code.patch` entries that insert, replace or delete whole lines when the presenter reaches `at_step` and are reverted when going back; the document is recomputed from the step-0 code every time (no diff of diffs). Targets are matched on the code as shown at that step and must match exactly once (`after`/`before`/`position` for inserts, `find`/`find_start`+`find_end`/`position` for replace and delete); load-time and `move.add` errors name the move. `typing: line|char` types the content in place in the TUI (`speed_ms` per unit; blank placeholder lines keep the layout steady; any key finishes it; the step's annotations appear when it ends). Annotations are authored against the code at their own step (`annotation.add` validates on that step's code) and shifted deterministically through later patches by the patch's own line map — never by a text search; one that loses every line is hidden and listed as `(unanchored)` in `scene.list`/`:list`, unless the move's `rebind` says where it goes. A `replace` keeps line-level annotations (note, box, callout, spotlight) on the same-offset line but unanchors column anchors (highlight, mark, arrow ends) unless `rebind`; `occurrence: N` (1-based over the whole code at that step; `end_occurrence` for `find_end`) picks a match on every text target and on `rebind` finds, which are validated when the move is added. Socket `move.add`/`move.delete`/`move.list`, MCP `add_move`/`delete_move`/`list_moves`, `scene.get` carries `moves` with the step-0 code embedded; the saved file and `:embed` always keep the step-0 code; `render --step N`, `.cast` and `.tape` apply the moves instantly; paste and follow are refused while a move is applied. Example `examples/ownership-moves.rs.codedraw`; undo covers moves and typing.
- Range anchors by two text markers (t-097): boxes, callouts and spotlights accept `find_start`/`find_end` on the socket and in the MCP tools, and `:box @'// begin'..@'// end' label` (also `:callout`, `:spot`) in the TUI; resolved at creation (first start anywhere, first end at or after it, same line allowed) and stored as lines plus `markers: {start, end}` on the annotation (shown in `scene.list`, dropped when the annotation is moved by lines). Without FILE it exports what the live instance is showing. MCP tool `export_image`. Fonts (JetBrains Mono + a symbols fallback) are embedded in the binary and in the SVG, so the image looks the same everywhere. New crate `codedraw-export`.
- `scene.get` sends the code embedded, so clients in another directory can render the live document.
- `update_annotation` (MCP) and `annotation.update` (socket, `move`) can move an annotation keeping its type, kind, style and label: `at` for highlights/marks/notes, `from`/`to` for arrows, `from_line`/`to_line` for boxes, callouts, spotlights and notes. Fields that do not apply to the type fail with `invalid_argument`; the MCP tool rejects unknown fields instead of ignoring them.
- `callout` annotation: a bordered multi-line paragraph explaining a range of lines, with optional title, `placement` (`margin`, `below`, `auto`) and `width`. `:callout A[-B] [@below|@margin|@auto] [title="…"] text`, `C` on a selection, `annotation.add` with `type: callout`, MCP `add_callout`. In the margin it reserves its rows and the neighbouring labels are drawn beside it instead of being pushed down; below, boxes extend around it. The ownership example closes with one (step 7).
- Default padding of one column at the left and right edges when the document sets none (`:pad 0 0` removes it, `:pad default` restores the default).
- `Tab`/`Shift-Tab` select an annotation in reading order; on it, `Enter` edits the label, `x` deletes, `c` changes the color, `+`/`-` move it between steps.
- Command line: `Tab` completes commands, mark kinds, annotation ids and themes; `↑`/`↓` browse the history.
- Padding around the drawing: `--padding V[,H]` when opening and `:pad V [H]` live; stored in the document (`padding: [v, h]`).
- Keyboard selection, vim style: column cursor with `h`/`l`/`w`/`b`/`e`/`0`/`$`, `v`/`V`/`i` selections, and selection actions `h` (highlight), `m` (mark, command line pre-filled), `n` (note), `b` (box), `a` (arrow in two selections), `s` (spotlight). Explicit anchors `L@S..E` and `L@C`. The annotation list moves to `L`.
- Generic, language-agnostic mark kinds (info, warn, error, ok, question, important, read, write, move, new, drop, scope, flow, todo) replacing the Rust-only set; Rust names remain as aliases. Custom styles in two modes: inline per annotation (`style: {glyph, legend, color}`, emoji allowed) and reusable document `styles` (`:style NAME …`, MCP `define_style`, `list_kinds`). `:mark 🔥 L:text legend` creates a one-off mark.
- `spotlight` annotation: a step that directs attention by dimming the code outside a range and/or the annotations outside a group (`:spot`, `:until`, `add_spotlight`, `annotation.add` with `type: spotlight`). The ownership example interleaves two.
- `code` as an object `{"file", "lines"}` with absolute paths or paths relative to the `.codedraw`; sidecars reference the source by default. `:embed` and `:link`.
- Step 0 = code only: `p` from step 1, `:step 0`, `--step 0` or `set_step 0` show the code without annotations. The ownership example starts that way.
- Clear annotations at once: `:clear [N|.]`, the `scene.clear` method and the `clear_annotations` MCP tool; reversible with `u`.
- Color per annotation (`color`: palette name or `#rrggbb`) in the model, `:color ID …`, API and MCP. Arrows without a color rotate through a palette so they can be told apart; the ownership example uses one color per value.
