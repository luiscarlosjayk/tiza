# Draw for a presenter

This page is for an agent (Claude Code, Zed, any MCP client) that is going to draw on the code a presenter has open in Tiza.

## Mental model

- The **TUI is the sole owner of the document**. You talk to it; you do not edit the `.tiza` by hand while it is open.
- A document has **code** (numbered lines, absolute numbering even when a range is opened) and **annotations**. Each annotation has a short, stable **id** (`a1`, `a2`… or the one you pass) and a **step** (1-based). Annotations with `step <= current step` are shown.
- **Anchors** are positions in the text: `{line, col}` or, better, `{find: "exact text", line?: N, occurrence?: K}`. `find` searches for the text on the given line (if you pass one) and then in the whole document. If it does not exist, the tool fails with `text_not_found`: do not guess columns.

## Recommended flow

1. `status` — confirm there is an instance and look at `cols`/`rows` and `warnings` (`N labels cut at C columns: a3, a5 (not drawn)` or `labels go under the lines at C columns` → keep labels short; `code needs N columns at C columns` → the presenter should widen the terminal to N columns or open a narrower range).
2. `get_code` — read the code with line numbers. Pick exact texts.
3. Annotate in the order of the explanation, assigning an increasing `step`:
   - `add_box {find_start, find_end}` (also `add_callout`, `add_spotlight`): two texts that delimit the range instead of line numbers — a comment marker (`// begin` … `// end`) or code (`fn takes` … `println`). The start is the first occurrence in the file, the end the first occurrence after it; a marker is plain text, so choose one that appears only where you mean it (the first `}` after `fn takes` may be inside a `println!("{s}")`). Errors name the missing marker. The markers are kept on the annotation (`markers`), so a later code change can re-resolve the range.
   - `add_mark` for semantic marks. Built-in, language-agnostic kinds: `info`, `warn`, `error`, `ok`, `question`, `important`, `read`, `write`, `move`, `new`, `drop`, `scope`, `flow`, `todo` (Rust habits work as aliases: `borrow`→`read`, `borrow_mut`→`write`, `lifetime`→`scope`). Each shows glyph + legend; `label` is appended. For something the author will reuse, `define_style` once (`{name, glyph, legend, color}`) and then use `name` as `kind`; for a one-off, pass `style: {glyph, legend, color}` inline. Emoji are allowed as glyphs. `list_kinds` shows what exists.
   - `add_arrow` for relationships (from where a value is born to where it is consumed). Style is the author's: `stroke` solid | dashed | dotted | thick | double, `route` rounded | sharp (a cell grid has no curves: rounded corners are the "curved" arrow), `head_start` / `head_end` none | arrow | dot | bar | open (default none → arrow; none + none is a plain connector). A convention that reads well: solid for a move, dashed for a shared borrow, thick for a mutable borrow. `update_annotation` changes them later (`stroke`, `route`, `head_start`, `head_end`); where a stub crosses another arrow's rail it breaks for one cell (the arrow passes under the rail); a box border is crossed with a junction glyph (┼ ╂ ╋ ╫ …).
   - `add_box` to delimit a function or a block. Boxes and callouts take `border` (solid | dashed | dotted | thick | double), `corners` (rounded | sharp) and `fill` (boxes are tinted by default, callouts are not); `update_annotation` changes them later.
   - `add_note` for a short sentence (one line, in the margin); `add_callout` for a paragraph of two or three sentences about a range of lines: it is a bordered block with an optional `title`, it does not displace the other labels, and `placement` is `margin` (default), `below` (own rows under `to_line`; inside a box only when the box contains the callout's whole range, otherwise after the box's bottom border) or `auto`. A `margin` block can leave fewer than 14 columns beside it. Then the labels of the lines that it covers go under their own lines. A `margin` block starts on the rows of its own line, beside the other blocks there. If it has no room there, it is drawn as `below`. It is never cut. Use `add_box` when you want to *delimit* code, `add_note` to tag a line, `add_callout` to *explain*; `highlight` for a fragment without semantics.
   - `add_spotlight` for a "look here" step: dims the code outside `from_line..to_line` and/or the annotations outside `ids` (and focuses the code of those annotations). It draws nothing; it directs attention. Active from `step` to `until`.
4. `set_step 0` leaves only the code (a good starting point for the take); then `next_step` as the presenter advances (or leave it in their hands: `n`/`p`). A document with named steps (below) also takes `goto_step {"id": "borrow"}`.
5. `check` before you show the document (or hand it back): the same preflight as `tiza check --json` on the live document. Errors are an anchor or marker that matches nothing, a move whose target does not match exactly once at its step, a linked file that cannot be read, an unknown or duplicate id; warnings are an annotation hidden as `(unanchored)` at some step, an annotation outside the `code.link` window of a step that shows its file (`outside_window`, from its own step on, with its lines carried there: kept, not drawn there; what the window of a later link never showed is the author zooming in and is not said, what a patch pushes out of it is), an annotation of a file its own step does not show (`not_shown`: `its file src/stack.rs is not shown at step 4 (src/queue.rs is)`, said even when that file shows at other steps, since it is never drawn at its own; one of the shown file outside the window is `outside_window` only), a label clipped with «…» at `width` (default 100, as `tiza render`; each one names its step, id and full text) and a step with nothing new. `min_clean_width` is the narrowest width from which no label is clipped: export at that width, or shorten the labels it names (`narrower`, when present, lists the narrower widths that are clean too, with the notes under the lines). A marker that matches more than once is a warning with its lines: the range takes the first match, so make it unique. The check runs inside the instance on the real code and linked files, so its spans and its answer are the same as `tiza check --json` on the saved file. Fix every error; warnings are the presenter's call. It reads only. It runs off the TUI thread, on a copy of the document, so the screen, the keys and your other calls are answered while it works; the reply adds `revision`, and the report is about exactly that revision of the document, never a mix of two. It is usually the one when you called, but a check that had to wait for another one runs on the newest copy asked for at its width, so its `revision` can be later than your call: trust `revision`, not the time you called; if a later change of yours returned a newer `revision`, check again. Checks do not stack: at most one runs and one waits. One with the same width and revision as the running one shares its run (`{}` is `{"width": 100}`); a check at another width while one already waits takes its place, and the replaced call is answered at once with `busy` (`check: replaced by a newer check (width 60) before it ran; ask again`): ask again.
6. `render_text` to see exactly what the audience sees and fix things. `export_image` with a `.png` or `.svg` path saves the scene as an image (fonts embedded; `step`, `width`, `theme`, `scale` optional) for thumbnails and docs; with a `.txt`, `.ansi` or `.md` path it writes the same scene as text (`.md` is a fenced block ready for a README, an issue or a chat message); with a `.gif` path it records every step of the document as an animated GIF drawn by Tiza itself (`interval` seconds per step, `skip_zero`, `scale` 2 by default, as for a PNG; the reply carries `frames` and `steps`) — nothing to install, no external tool. MP4 is a shell command (`tiza render --out demo.mp4`, needs the presenter's ffmpeg), not a tool. It draws the live document as the TUI has it, the files a `code.link` shows included (the instance sends them with the scene), and every call answers: with the file written or with an error, never a call left waiting. It renders off the server's own threads, so `status` and the other tools keep answering while it works; one that takes longer than 120 s is abandoned with an error saying so and writes nothing (export a still, fewer steps or a smaller scale, or ask the presenter to run `tiza render` in a terminal, which has no deadline). A `step` past the last one exports the last and the reply says so in `warning` (and `step` is the step exported); `interval` takes 0 to 3600 seconds.

## Example (ownership)

```json
{"name":"add_mark","arguments":{"kind":"move","at":{"line":3,"find":"s"},"label":"s moves into takes","step":1}}
{"name":"add_arrow","arguments":{"from":{"line":2,"find":"s"},"to":{"line":15,"find":"s: String"},"label":"move","step":1,"color":"orange"}}
{"name":"add_arrow","arguments":{"from":{"line":7,"find":"&t"},"to":{"line":19,"find":"s: &String"},"label":"shared borrow","stroke":"dashed","step":3}}
{"name":"update_annotation","arguments":{"id":"a2","stroke":"thick","head_end":"bar"}}
{"name":"add_note","arguments":{"line":4,"text":"s no longer owns it: using it here does not compile","step":2}}
{"name":"add_box","arguments":{"from_line":15,"to_line":17,"label":"takes owns s and frees it at the end","step":2}}
{"name":"add_callout","arguments":{"from_line":15,"to_line":25,"title":"three ways to pass a value","text":"takes(s) moves the String. len(&s) borrows it read-only. push(&mut s) borrows it mutably.","placement":"auto","step":3,"color":"cyan"}}
```

## Emphasis

`highlight` and `add_mark` take `emphasis`: `fill` (the default tint), `underline` (a thin ‾ row under the span, good for "look here" without hiding the syntax colors), `brackets` (⌈ ⌉ beside the span; a side glued to other text goes to the row below, code is never covered) and `strike` (struck through, for "this line is gone"). The emphasis glyphs and the struck text are drawn in a softened shade of the annotation's colour (the span's own text keeps the full colour for underline and brackets), so they point without shouting; struck text still reads at the 4.5:1 code contrast. `update_annotation {"id", "emphasis": "strike"}` changes it later. Omitted means fill, and fill is not written to the file.

## Color

Every annotation accepts `color`: `orange`, `blue`, `green`, `purple`, `pink`, `cyan`, `yellow`, `red`, `gray` (Spanish aliases such as `azul`, `verde`… also work) or `#rrggbb`. Use it to tell a story per value: everything that happens to `s` in one color, everything about `t` in another. Arrows without a color rotate through an automatic palette; boxes, notes and highlights without a color use the theme's. `update_annotation` with `color: ""` returns to automatic.

## Fixing a misplaced annotation

`update_annotation` (socket `annotation.update`) refuses a key that it does not know with `invalid_argument`, and names the key. To change the text of a note or a callout, send `label`. `update_annotation` moves an annotation without recreating it, so it keeps its id, kind, style, label, color and place in the list: `at` for highlights, marks and notes (`{"id": "a1", "at": {"line": 15, "find": "s: String"}}`), `from`/`to` for arrows, `from_line`/`to_line` for boxes, callouts, spotlights and notes. A field that does not apply to the annotation's type fails with `invalid_argument` (e.g. `from_line` on a mark), and unknown fields are rejected, so a call that returns a new revision did change something. Over the socket the same goes under `move`: `annotation.update {"id": "a1", "move": {"at": {...}}}`.

An update changes only what you send. Without `step` and `file`, the annotation keeps its step and its file, also at a step that shows another file. `annotation.update` (MCP `update_annotation`) takes `file` to move the annotation to another file: a linked file as the `code.link` names it, or `null` for the main file. Tiza checks the annotation on the code of that file at its step. `scene.patch` does the same for an id that the document has. Without a `step` or a `file` key, the annotation keeps its step or its file. A `step` that you send stays as it is, step 0 too. `scene.patch` takes the same names of a linked file as `annotation.update`. A new id gets the defaults of `annotation.add`. Step 0 goes to step 1, and without `file` the annotation gets the file shown at its step. `file: null` has two meanings. In an update, or in a patch of an id that exists, it is the main file. In `annotation.add`, or in a patch of a new id, it is the file shown at its step.

## Is it on screen?

`annotation.add` and `annotation.update` (and every MCP `add_*`, `highlight` and `update_annotation`) reply with where the annotation stands against the view at the moment it is applied: `{"id": "a17", "revision": 42, "step": 1, "shown_step": 0, "visible": false, "hidden": "it appears at step 1"}`. `step` is the annotation's step (a new one at step 0 still goes to step 1, and the view stays at 0), `step_title` is added when that step is named, `shown_step` is the step the view was showing, and `visible` says whether it is drawn there. When it is not, `hidden` says why in words: `it appears at step 3`, `its file src/queue.rs is not shown at step 2 (main.rs is)` (a `code.link` shows another file at that step), `its lines are outside the code shown at step 2 (10-36)` (outside the link's window), `it lost its anchor at step 2 (unanchored: …)`, `a spotlight shows only at its step 1`, or `it is not drawn: no room for its text at 98 columns (check at width 98 lists it)` (a note or a callout the layout leaves out at the size of the presenter's screen). If its own step shows another file, `hidden` gives that reason for its step, not `it appears at step 3`. `visible` looks at the layout too, as presentation mode, `export_image` and `check` lay the step out (once its typing is done): at the screen's code area, the terminal less its side padding (98 on a 100-column terminal with the default padding, 96 with `padding: [1, 2]`), kept within the widths `check` takes (20-400), so `check` at the width the text names says the same. While authoring, before the last step, the presenter's own screen can place a label a few columns otherwise (it keeps room only for the steps so far); the reply is about what the audience sees. It is the size at that moment: a resize afterwards changes the screen, not the reply (the next `update_annotation` answers for the new size); with no terminal size known it is `check`'s default width, 100, and the text names it. A box, an arrow, a highlight or a mark is drawn even when its label is not, so it stays visible and `clipped` says what happened to the label: `its label is cut with … at 98 columns (check at width 98 lists it)` or `its label is not drawn: no room at 98 columns (…)`; a label drawn whole has no `clipped`. To fit it, shorten the text or ask the presenter for a wider terminal (`check` says the width every label fits). The MCP tools put it in one sentence before the JSON: `a17 added at step 1; not visible now: the view is at step 0 and it appears at step 1 (next_step shows it).` A hidden annotation is not an error: say so to the presenter instead of adding it again, and do not move their view yourself unless they asked. The presenter is told too: their status bar says `a17: box 3-5 added by agent (step 1, press n)`, or `a3: note L2 added by agent (not drawn: no room at 98 columns)` (several of yours within a second share one message, `3 agent annotations not shown (step 1, press n)`; in presentation mode it waits until they leave it), so there is no need to repeat it in the chat unless they ask. If the annotation's step shows another file, the bar names that file: `a17: box 3-5 updated by agent (main.rs, not shown at step 3)`. In supervised mode the reply is computed when the presenter accepts the proposal, so `shown_step` is the step on screen at that moment, which may not be the one you saw when you asked; the view can move again right after, so read `visible` as a snapshot. `annotation.delete` still replies `{id, revision}`.

## Pointing live

`point_at` (socket `pointer.set`) is a laser pointer on the presenter's screen: the line you name stays as it is and the rest of the code dims while you talk about it. Give `{"line": 7}`, `{"line": 7, "find": "takes(s)"}` (the text must be on that line), `{"find": "takes(s)"}` (it must appear once in the code shown; otherwise `invalid_argument` lists the lines) or `{"from": 15, "to": 17}`. The view scrolls to it and the presenter's cursor moves there, so their `j`/`k` go on from your line. `clear_pointer` (`pointer.clear`) turns it off. It is the same pointer as the presenter's `f` key: the last one wins — when the presenter moves the cursor the pointer follows them (`status.pointer.by` goes from `agent` to `presenter`), and `f` turns yours off. `status` carries `pointer` (`{"line": 7, "to": 7, "by": "agent"}`) or `null`. The reply's `shown` is `false` while the presenter has the command line open: it shows when they close it. On `n`/`p` it stays on its line (carried through the moves of the step) and goes off when that line disappears.

Point instead of adding a spotlight when the focus is for this moment of the conversation, not for the recording: the pointer creates nothing — no annotation, no revision, no undo entry, no autosave — and no export, GIF, `.cast`, `.tape`, MP4 or `render_text` draws it. Use `add_spotlight` when the focus belongs to a step and must be in the take.

## Between takes

`clear_annotations` empties the canvas at once (or only one step with `step`). The presenter can undo it with `u`, so it is not destructive live.

## While the presenter edits

`set_follow {"enabled": true}` makes the TUI reload the code every time the source file is saved (the presenter can also type `:follow on`). The reply comes at once and says `following main.rs`, because the file watcher starts on a thread of its own. A save made while the watcher starts loads when it runs. If the watcher cannot start, follow turns off: the bar says `follow off: cannot watch …`, and `follow.status` gives `enabled: false` and `reason: "cannot watch …"`. At a step with moves applied it turns on and waits: a save is not loaded there, the code on screen stays (embedded in the `.tiza` meanwhile) and the first step with no moves applied loads it as one reload; the reply's `message` and the bar say `following main.rs (waiting: moves applied at step 1; loads at step 0)`, and `follow.status` gives `enabled: true` with that `reason` (`loads at step 2 or earlier` when the first move is at step 3: a save loads at any step before the first move). Annotations stay anchored to their text; the ones whose text disappears are dropped, and the reply (same as `follow.status`) reports `reloads` and `last_reload`, so after a save you can call `list_annotations` to see what survived and re-add what matters. It fails with `invalid_argument` when the code is embedded in the document and no followed file is known (read from stdin, or frozen with `:embed`); embedded code that replaced a followed file (a paste, an undo past a reload, while `follow.status` gives that file's `path`) is not a failure: the call loads that file over it, as below. A paste by the presenter turns follow off, since the pasted code is theirs and a save must not replace it: `follow.status` then says `enabled: false` with a `reason` (`the code is pasted, not main.rs; :follow on reloads main.rs`), and `set_follow {"enabled": true}` loads the file over the paste as one reload the presenter can undo. The same happens when the presenter's `u` (or redo) brings back code the file no longer holds, such as the code from before a reload: the code stays embedded in the `.tiza`, follow turns off and `reason` says `the code on screen is not main.rs; :follow on reloads main.rs`. The `reason` always describes the code on screen now, and is absent once the file holds that code again; a `scene.get` → `scene.put` of such a document keeps the code embedded. The `.tiza` names that file in `follows` (`{"file": "main.rs"}`, written only with embedded code), so `set_follow` still loads it after the document is reopened; `scene.get` carries `follows`, and a `scene.put` that sends it sets the file `set_follow` reloads (a put of another document without it follows nothing).

A reload or a paste re-anchors every annotation by its text; one whose text is gone is dropped and the presenter is told.

A reload or a paste is not written by the demo, so a move follows it only where that is exact: the old and the new code share a start and an end, those lines are the same lines (the end moved by what the change added or removed), and a move's line numbers there (`position`, a `cursor` line, a `select` by line) get the new numbers — a line pasted above a target moves it down with its text, even when other lines hold the same text. The rule underneath: **if the place of a line is ambiguous, the move is stale** — a line of the common start or end next to the change whose text the change repeats (a function pasted next to a copy of itself) has no known place. This reads the change as the smallest one: one block, or several edits that share lines. A longer history that leaves the same text in the same place cannot be told apart from text alone: `---`, `old`, `---` → `---`, `new`, `---` with a move on L1 reads as «line 2 changed», but if the first two lines were in fact deleted and `new`, `---` appended, the move lands on the other `---`. That needs a file with the same text at both ends; in documents edited while Tiza is open, prefer `find` to `position`. Deleting a block identical to its neighbour leaves the move on the copy that survives, without a mark, while pasting such a block next to it marks the move: the rule is never to choose between equal lines of the new code, and after a deletion only one is left. The change is one block when its old and new lines share no line; when they share one there were several edits, and every target from the change down is **stale** even when the text there looks the same (a target inside a one-block change is stale unless the block kept its size, line for line), and so is one whose lines no longer hold the text they held; a text target is stale when it now matches nothing or more than once, and a move whose target a stale one wrote is stale too. A stale move is skipped when stepping (the steps keep their numbers), kept in the file as written (only its line numbers follow a change whose shift is exact), and named on the presenter's bar once per change (`stale move skipped (u undoes or re-add): #1 (L2 changed)`); annotations on lines a stale patch writes are hidden as `(unanchored)`, not drawn on other text, and come back on what it writes when it matches again. `list_moves` gives `stale: true` and `stale_reason`, `list_annotations` lists the stale moves last as `move #N … (stale: why)`, `status` has `stale_moves`, and `check` reports each one. A later reload or paste that makes the move match again clears the mark (`move #1 matches the code again`), and so does `u`; code put back exactly as it was when the move last matched (a checkout, a stash, the editor's undo) gives the move back with its numbers. An `add_move`/`delete_move` or a `scene.put` re-checks only text targets: a stale move on line numbers stays stale until the code says where its lines are. The marks are the live instance's only: `scene.get` sends them next to the document (`stale`, `held`), never in it, so `export_image` skips what the screen skips and a `scene.put` of that copy keeps the same moves stale. After closing Tiza a move by line numbers whose lines changed loads and applies on the lines now there without a word (a text target that matches nothing is still a load error): **in a document that reads its code by reference (the author keeps editing the file), target moves with `find` rather than `position`**, run `check` on the live instance before it closes, or check the moves by line number after editing with Tiza closed. To fix a stale move, `delete_move` it and `add_move` it again on the code as it is now (unlike a reload, an `add_move` before other moves does carry them, see below).

## The presenter's screen

**Themes.** `set_theme` takes `dark`, `light`, `terminal` (the host's palette), `auto` (follow the terminal's background) or `toggle`; the reply says whether the instance is following (`auto`). A document may carry `theme_overrides` (per-token colours); `export_image` applies them and, for a terminal theme, paints the matching dark/light palette instead — there is no host palette in a file.

**The margin is the presenter's too.** `status.margin` is the cap on the right margin when one is set (`scene.patch {"margin": 24}` sets it, `null` removes it); long notes wrap at it. Keep notes short either way — a wrapped note takes rows from the lines below it.

**The gutter is the presenter's.** `status.numbers` says whether line numbers are shown; `scene.patch {"numbers": false}` hides them (saved in the document, so every export follows). Line numbers in your anchors (`line`, `find`) are the real ones whatever the gutter shows.

**One geometry per take.** `render_text` is the take, the same text `tiza render --format txt` writes for the step: without a `width`, at the width of the screen's code area (the terminal minus its padding); with a `width`, at that width. Without a `width` it agrees with the `visible` of your add calls, and `check` at that width gives the same verdict; a second line of its result names the width. During a typing animation it is the step as it is once typed. `render_text` and `export_image` size the arrow lanes, the box band and the margin for the maximum over every step of the document, the same way presentation mode does: a frame at step 1 and one at step 7 put the code at the same x, so you can compare frames and build thumbnails that line up. The presenter's authoring screen may look narrower than your render at an early step; that is the dynamic layout, not a bug, and `:layout stable` on their side makes the two agree.

**Secrets on screen.** What `get_code` returns is what the audience sees, in every export and recording. If the code you read holds a real secret (a token, a password, credentials in a URL), say so to the presenter before anything is recorded and do not repeat it in a note or a label; demos should use fake values. A value outside a fixed set (a color, `border`, `corners`, `stroke`, `route`, a head, `emphasis`, `placement`, a mark `kind`, `theme`, a move's `action`/`op`/`typing`/`position`, a method name) is never repeated in an error: the message lists the valid names (`unknown border (use solid, dashed, …)`, `invalid parameters: unknown variant «…», expected one of …`). A value of the wrong type is named, so you can see what you sent (`invalid type: string "three", expected u32`; cut at 40 characters with `…`).

**What stays local.** Everything you send over the socket or the MCP stays on this machine: the `tiza` binary has no network dependencies and never opens a connection ([Privacy and network](../concepts/privacy-and-network.md), [ADR 0009](../adr/0009-politica-de-red.md)). Your `add_note`, the code you read with `get_code`, the exports you request — none of it leaves the presenter's computer unless *they* run a separate `tiza-net` command on purpose. Do not expect a `publish` or an `upload` tool here, and do not try to reach the network on Tiza's behalf: if the presenter wants a GIF on a service, produce the file locally and tell them which command would send it.

**Saving rule.** The TUI writes every change to the `.tiza` sidecar of the file that is open — your `add_note` lands on disk at once — unless the presenter opened it with `--no-save` or turned `:autosave off` (`status.autosave` tells you; `:w` is theirs), or the sidecar cannot be written (a read-only file or folder: the presenter is told once, the bar shows `read-only • unsaved (:w)`, your calls keep succeeding in memory and `:q` refuses until they `:saveas PATH` (saving there from then on) or `:q!`; the next autosave that works clears it). `scene.put` of a document from **another source** (a different `source.path`, or embedded code with none) is shown but never autosaved over the file that was open: autosave stops with a message, and the presenter decides with `:w` (over the open file), `:saveas PATH` (elsewhere, saving there from then on; `:w PATH` only writes a copy, as in Vim). A relative path starts at the folder where you started Tiza, and Tiza creates the folders that are missing or `:autosave on` (resume). Follow, if it was on, goes off (`follow off: the code on screen is not main.rs`): the file it watched is not the one on screen. A put of the same source — re-putting an edited copy of the open document, `scene get` → `scene put` — keeps saving as before, and **the files the open document reads stay references**: `scene.get` always hands the code out embedded (`code` and every linked file under `views`), and when what comes back is the same as that file's text **now**, the `.tiza` keeps `"code": {"file": …}` (with its `lines`) and its `code.link` paths, and only what you changed changes. It is a plain comparison of the code you send with the file on disk — nothing is remembered between your `scene.get` and your `scene.put`. Code you did change is shown but never autosaved over the file it came from: autosave stops and the bar says which file (`not saved — autosave off: the code sent for main.rs differs from the file on disk …`); to change the code itself, edit the file (or add a move). If the file changed on disk after the instance loaded it and you send back the copy `scene.get` gave you, the document still reads the file (it is never embedded in silence): the screen keeps the copy loaded and the bar says `main.rs changed on disk since it was loaded: still read from it …`. With follow on (`status.follow`) the screen shows the file as it is, so a put whose code is not the file's is refused (`the code sent is not what main.rs holds now, and follow is on …: scene.get again`) and nothing changes. A put is refused too when a file the document reads can no longer be read (`main.rs cannot be read …`). A `views` entry that no `code.link` names is ignored. A put that changes nothing writes nothing. After a put of edited code, a put of the file's own code makes it a reference again (with autosave still off, the bar says `main.rs is a reference again; autosave still off (:autosave on resumes)`). A document with embedded code (read from stdin, or frozen with `:embed`) stays embedded. `u` after a put brings the previous document back, step included. From the CLI, `tiza scene put FILE` takes a `.tiza` or the `scene get` envelope and refuses anything else unless `--as-code` is passed.

## Idempotency

Pass your own `id` (`"id": "move-s"`) so that a retry does not duplicate the annotation: the second attempt fails with `duplicate_id` and you can move on.

## Finding the tools (deferred tools)

A client may defer MCP tools and load only their names and the server `instructions` at the start (Claude Code's tool search, on by default), so the instructions are written to be searched by: what Tiza is, when to use it (explain code to a person or another agent, live or recorded, step by step), the words people use for it and the flow in two lines. `status`, `get_code`, `render_text` and `add_box` carry `_meta["anthropic/alwaysLoad"]: true`, which asks such a client to load them upfront, so the first call needs no search; the others (`add_arrow`, `highlight`, `add_note`, `add_move`, `export_image`…) are found by searching for what you want to draw. A client that does not know the key ignores it and loads every tool as before; in Claude Code the person who configures the server can override it for the whole server (`alwaysLoad` in its entry).

## After a rebuild

`status` returns a `bridge` object: `version`, `build` (git commit of this MCP server) and, when the `tiza` binary on disk is newer than the running server, `binary_rebuilt: true` plus a `hint`. That means the tool list you hold may be stale: tell the user to reconnect the server (Claude Code: `/mcp` → tiza → reconnect) before relying on a tool you cannot see. `instance_build` appears when the TUI was built from a different commit than the bridge: ask the user to restart the TUI as well.
