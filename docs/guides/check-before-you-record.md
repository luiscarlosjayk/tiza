# Recommended recording profile

Do these checks before you record a video or a GIF.

**Before you record**, run `tiza check demo.tiza`: it loads the document as the TUI does and lists every problem at once — an anchor, marker or move target that no longer matches (or matches twice) at its step, a linked file that cannot be read, an unknown or duplicate id (errors, exit 1) — and what would spoil the take: an annotation a move hides, one outside the `code.link` window of its own step or pushed out of it by a later patch, one of a file its own step does not show (said even when that file shows at other steps, since it is never drawn at its own), a label clipped with «…» at the width you record at (100 unless `--width N`), a step where nothing changes (warnings; `--strict` fails on them too). A marker (`find_start`/`find_end`) that matches more than once is a warning with the lines it is on (the range takes the first match). It ends with the narrowest width from which no label is clipped (`examples/ownership.rs.tiza` says 91); below the width where notes move under their lines a narrower take can be clean again, and when you ask for one of those it says so (`--width 80`: `no label is clipped at 91 or wider; 70-84 are clean too (notes go under the lines below 85 columns)`). `--json` gives the same findings to a script; it writes nothing. A live instance answers the same report for the document it holds, unsaved changes included: `tiza api check '{"width": 108}'` (the MCP `check` tool).

Use demo values for tokens, passwords and credentials in anything you record: what is in the file is what the audience sees. Full-screen terminal or 50 % next to Zed, 18–22 px font, snippets of ≤ 60 columns. The status line shows `cols×rows`, and a `!` badge only when the step on screen loses something: `! 3 labels cut` (labels or notes cut with `…` or not drawn) or `! code needs 83 cols` (a code line is clipped: 83 is the terminal width from which the step shows every code line). `status` over the socket lists the details in `warnings`; below ~100 columns, notes are drawn under the line instead of in the margin (an arrow's label then sits on the arrowhead's row right after the code when it fits, or on the row below behind the arrow's own glyph — `─▶ move` — so it reads as the arrow's, never as a loose comment), and callouts with `placement: auto` move below their lines. One blank column is kept at each side by default (`:pad V H` to change it, `:pad 0 0` to remove it, `:pad default` to go back). Both themes use explicit RGB colors designed for 1080p and checked after YouTube-like compression (`scripts/legibility.py`, run in CI: every text color keeps ≥ 4.5:1 against the background). The terminal font is yours: the exports set everything — code, notes, labels and legends — in JetBrains Mono, so using it in the terminal too makes the live session and the exported stills match; any other monospace works just as well.
