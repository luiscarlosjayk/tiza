# ADR 0007: Moves and named steps (scripted demos without an editor)

> Renamed: the project became **Tiza** on 2026-10-17 ([ADR 0008](0008-renombre-a-tiza.md)). Where this record says CodeDraw, read Tiza; `codedraw` → `tiza`, `.codedraw` → `.tiza`, `CODEDRAW_*` → `TIZA_*`.

- Status: accepted (2026-10-16, reviewed by Luis with three changes: deterministic re-anchoring, explicit `step` on named steps, follow/link while moves are applied; 2026-10-17, four corrections: column anchors on replaced lines, `occurrence`, no speaker features, t-106 later; 2026-10-18, §3(f) rewritten with t-105: one view per file, annotations belong to a file)
- Board: t-084; unblocks t-097 → t-098 → t-105 → t-099 → t-101 → t-106 (see Consequences)
- Research: [docs/research/demo-time.md](../research/demo-time.md)

## Context

Demo Time (VS Code) scripts a demo as scenes of *moves*: open a file, type code, highlight, run a command, show a slide, advance with →. CodeDraw already has the static half — a step is a set of visible annotations — and a remote control (socket, MCP, keyboard). What a presenter misses is the dynamic half: **the code itself changing while they talk**. None of that needs an editor: CodeDraw owns the buffer it shows.

**Product criterion (Luis, 2026-10-17): be selective.** Of everything Demo Time does, CodeDraw wants exactly two things: (a) **switching between files during the presentation, each file with its own annotations**, and (b) **modifying the code progressively, with the annotations following the change**. Nothing else: no snippets, no presenter notes, no timer, no clicker, no terminal actions. Everything below serves (a) and (b); named steps and auto-advance exist only as automation for recordings.

## Decision

1. **Annotations and `step` stay as they are.** A step is still a state: "annotations with `step <= current` are visible".
2. **`moves`** is an optional list in the `.codedraw`. A move runs when the presenter *reaches* `at_step` going forward and is reverted when going back, so the document is a pure function of the step: `render --step N` applies moves `≤ N` instantly.

   ```json
   "moves": [
     {"at_step": 3, "action": "code.patch", "op": "insert", "position": "7",
      "content": "    let n = len(&t);\n", "typing": "line", "speed_ms": 400},
     {"at_step": 5, "action": "code.link", "file": "src/stack.rs", "lines": "7-30"},
     {"at_step": 5, "action": "cursor", "line": 12},
     {"at_step": 6, "action": "select", "from": {"find": "&mut u"}, "to": {"find": "u);"}},
     {"at_step": 6, "action": "wait", "ms": 800}
   ]
   ```

   (`position` is always a string: `"7"` or `"7-9"`; the loader rejects a bare integer.)

   Actions, deliberately few: `code.patch` (`op: insert|replace|delete`; an insert targets the line it goes before with `position` or the text of a line with `after`/`before`; a replace or delete targets `position` (`"7"`, `"7-9"`), `find`, or the `find_start`/`find_end` markers; `typing: instant|line|char`), `code.link` (show another file — a *view*, §3f — with `lines` as an optional window), `cursor` (`line`, `col`), `select` (`from`/`to`, each a `find` or `line`/`col`; with `find`, from the start of the first text to the end of the second), `wait` (`ms`). Several moves at one step run in list order. Moves at step 0 are rejected: step 0 is the untouched code. `cursor` and `select` are state the step leaves (a `code.link` clears them; a later patch of the same file shifts them like an arrow's ends, and a selection whose text a patch replaces is dropped); the TUI moves its cursor there and draws the selection, `render --step N`, `.cast`/`.tape` and the image exports draw both. `wait` is part of the step's animation like typing: the step's annotations appear after it in the TUI and the GIF, a `.tape` sleeps through it, a `.cast` holds the step's frame that much longer, and a still render ignores it.

   **`occurrence`:** every text target of a move (`find`, `find_start`, `find_end`, `after`, `before`, and the `find` of `select` and `rebind`) accepts an optional `"occurrence": N`, **1-based, counted in reading order over the whole code as it is at that step** (not per line): `{"find": "}", "occurrence": 3}` is the third `}` of the file at that step. Without it, more than one match is a load-time error; with it, the N-th match is used, and an N beyond the number of matches is a load-time error naming the move.
3. **Re-anchoring after a `code.patch` is deterministic, never fuzzy.** The patch is known, so it *is* the position map — no text search decides where an annotation goes.
   - (a) **Default, zero authoring:** positions are shifted by the patch's own edit, like tracked markers in an editor. An insert of N lines at line L moves every anchor at `>= L` down by N; a delete of lines `A-B` moves anchors after B up by `B-A+1`; a replace is a delete plus an insert. For the lines a `replace` overwrites: **line-level** annotations (notes, boxes, callouts, spotlights) map to the line at the same offset inside the new text (a range that loses its last lines shrinks to the ones left); **column-anchored** annotations (highlights, marks, arrow endpoints) are unmapped — the new text is different, so a column in it means nothing — and go `(unanchored)` unless a `rebind` covers them. Anchors before the edit never move.
   - (b) **Explicit rebind:** for text the patch replaces or deletes, the move may say where each anchor goes, with the same fields as `annotation.update`'s `move`: `"rebind": {"<annotation id>": {"at": {"find": "...", "occurrence": N}}}` (or `"at": {"line": N, "col": C}`) for highlights, marks and notes; `{"from": {...}, "to": {...}}` (each a `find` or `line`/`col`) for the two ends of an arrow; `{"from_line": A, "to_line": B}` for boxes, callouts and spotlights. A field that does not apply to the annotation's type is an error, never ignored. A `find` is resolved against the code *after* the patch, must match exactly once (or carry `occurrence`), and an ambiguous or missing match is a validation error when the document loads (`scene.list` names the move and the id), not a silent guess.
   - (c) **Unanchored, never deleted:** an annotation the patch unmaps and no `rebind` covers is hidden, listed as `(unanchored)` in `scene.list`, kept in the file, and comes back untouched when `p` reverts the move (the document is a pure function of the step, so going back restores the exact previous state).
   - (d) **Coordinate rule:** an anchor is always written against the code *as it is at the step of its annotation*. An annotation created at step 4 is authored on the step-4 code — the code *as shown* at step 4, after that step's own moves — and never needs to know the step-1 code; moves at steps `<= 4` have already been applied when it is resolved, moves at steps `> 4` shift it from there. Agents therefore read `get_code` at the step they are annotating. *Added by t-188 (2026-10-20):* a `code.patch` added later changes the code those anchors were written against, so `move.add` carries every annotation of its file at its step or later, and the line numbers of the moves that run after it (`position`, `cursor`, `select` by line, a `code.link` window), through the new patch by line identity — each line is the step-0 line it was or the patch that wrote it, never a text search — and `move.delete` carries them back, so deleting a move gives back the document from before it. An insertion point is held by the line before it; lines inserted inside a later move's range go with that move. A change that would lose something refuses itself, naming it: an anchor's text, a range's or a window's first or last line, the line a later insert goes after, a later move's text target that would match another line, a `rebind` line it would shift (rare, so refused rather than carried), a later move a deleted `code.link` would stop applying, or the annotations of a file whose only `code.link` is deleted.
     *Added by t-194 (2026-10-21):* an insert right before a window's first line **at the link's own step** grows the window to start at the inserted lines (`17-23` → `17-24`), so what that step adds is seen there; at any other step the window is carried like the other numbers, and deleting that insert gives the window back (the inverse rule: a window that starts on the first line an insert of its step wrote starts, without it, at the line after). Nothing stops being drawn without saying so: an annotation whose own step shows another file (said even when that file shows at other steps, since it is never drawn at its own) is a `check` warning (`not_shown`), and a `move.add` or `move.delete` that leaves one so says it in its `warning` and is made, as for a window; deleting the only `code.link` of a file stays refused, because its annotations would belong to no view and the saved `.tiza` could not load them.
   - (e) **The fuzzy matcher is not for moves.** `reanchor.rs` (t-010 paste, t-011 follow: line diff, nearest match, same occurrence) exists for changes CodeDraw did not author. A move is authored, so it carries its own map; mixing the two would make a demo's outcome depend on the surrounding text.
   - (f) **One view per file; annotations belong to a file (t-105, confirmed by Luis 2026-10-17).** The document's own code is view 0 (the main file). Every `code.link {file, lines}` names a view by its **file only**: `lines` is a window that crops what is shown, so `stack.rs:1-20` and `stack.rs:20-40` are the same view, and linking the main file again (`file` equal to `code.file`, or a path suffix of the source path) is a view change back to view 0, never a new file. A view's code is the whole file, read next to the `.tiza` like `code.file` (relative paths resolve against the document's directory) or taken from `views` when `:embed` froze it (`"views": {"src/queue.rs": [lines…]}`, one entry per file; the window stays in the move); a link to a file that cannot be read is a load-time error naming the move and the path. Each annotation carries an optional `file` (absent = the main file), filled in automatically from the view shown at its step when it is added without one, so a `:box 12-18` typed while `queue.rs` is up, or an `add_box {step: 2}` at a step that shows it, belongs to `queue.rs` without anyone naming it; its lines are **real file line numbers**. Visible at step N = `step <= N`, same file as the view shown at N, and inside the window; an annotation of the shown file outside the window is simply not drawn, and one of another file is not shown — neither is `(unanchored)`, both come back untouched when the demo links back or `p` reverts the link. `(unanchored)` stays a `code.patch` matter: a patch edits the file shown at its step (its own base plus its patches `<= N`, whatever window is up; the same pure-function rule per view), is validated against that file, and shifts only the annotations of that file (rule d holds per view). `scene.list` names the file of every annotation of a linked file (`a4 [step 3] box L15-17 (queue.rs)`), the status line shows `↪ file:A-B` while a link is up, and `code.get`/`status`/`move.list` report the view (`file`, `view`, `first_line`, `last_line`). The alternative — one `.tiza` per file plus a link that opens the other document — was discarded: it splits one act into several files (§5).
   - This replaces the "first occurrence" rule of the original proposal: a `find` in a *move target* (`code.patch` with `find`, `select`, `rebind`) must match exactly once in the code at that step; several matches are a load-time error, so the author disambiguates with `occurrence` (1-based over the whole code at that step, see §2) or a longer text.
4. **Named steps carry an explicit `step: N`.** Optional `steps: [{"step": 3, "id": "borrow", "title": "Shared borrow", "auto_advance_ms": 3000}]`; the number, not the position in the array, binds a title and `auto_advance_ms` to a step, so inserting or moving a step with `+`/`-` does not shift them. Entries may be sparse (unnamed steps show only their number) and are kept sorted by `step` on save. The status line shows the title; the socket gets `step.goto {id}`; the MCP gets `goto_step`; the CLI gets `codedraw next|prev|goto ID`. `loop: true` is a document field. All of this is **automation** (unattended recordings, a looping booth screen, an editor task that advances the step), not speaker tooling: there are no presenter notes, no timer, no clicker or remote-control feature (decided 2026-10-17).

   *Implemented by t-099 (2026-10-18):* ids are unique, one word, never all digits (a number in `goto` always means a step number) and never starting with `-` (the command line would read `tiza goto -1` as an option); two entries for one step, a duplicate, a digit-only id or one starting with `-` fail to load (and `scene.patch` refuses them with `invalid_argument`); an entry for a step past the last one is **kept and warned** (on open in the TUI, in `status.warnings`, on stderr by `render` and as a warning by `tiza check`), never dropped and never a load error — deleting the last step's annotations must not make the file unloadable. A key an entry has that Tiza does not know (the dropped `timer_min`, a typo, a field from a newer version) is kept in the file as written, never used, and warned about in those same four places (on open in the TUI, `status.warnings`, `render` stderr, a `tiza check` warning — exit 0, 1 with `--strict`); it is never a load error and never ignored in silence. `step.goto` / MCP `goto_step` take an id or a step number; any other value (`-1`, `4.5`, `null`) is `invalid_argument` with the message "`id` must be a step id or a step number from 0 to N" (N the last step). `goto` (`step.goto`, MCP `goto_step`, `tiza goto`, `:goto`) recomputes the document from step 0 like any step change and lands with the step's typing complete. `auto_advance_ms` counts from when the step is ready (typing and `wait` moves done), is held while the `:` line, a `v`/`V` selection or an overlay is open, and fires once per arrival; `loop` wraps forward only (`p` at step 0 stays). Decided by Luis (2026-10-18): the native GIF and MP4 hold a step with `auto_advance_ms` for exactly that long and `--interval` for the rest; a `.tape` therefore sends no `n` after such a step, and the `.cast` keeps `--interval`.
5. **One file per act.** Moves live inside the `.codedraw` (schema stays 1: all fields optional and ignored by older readers). A separate "play" file that sequences several documents is not needed yet; `code.link` covers "now show this other file".
6. **What stays with the editor.** Opening files in the editor, running terminal commands, zooming the editor font, slides. t-099 shipped the `tiza next|prev|goto` CLI and docs/zed.md now lists Zed tasks for it (not yet run in Zed); pairing one with the editor's own action stays the author's.
7. **Follow mode and `code.link` while moves are applied.** A demo owns its buffer; the file on disk is only the step-0 code.
   - While any move is applied (current step ≥ the first `at_step`), **follow is paused**: file saves are noticed but not loaded, the status line shows `⟳ following (paused: moves applied; step back to 0 to reload)`, and `follow.status` reports `paused: true` with the reason. Going back to a step with no moves applied resumes follow and, if the file changed meanwhile, reloads it then, re-anchoring the step-0 annotations with the fuzzy matcher as usual (rule 3e: that change was not authored).
     *Implemented by t-206 (2026-10-21):* the pause is the bar's notice (`main.rs changed on disk but moves are applied at step 2: go back to step 0 to reload`); while a change waits, the code on screen is saved embedded (as after a paste), so the `.tiza` never pairs the annotations and `rebind` entries made for it with a file that holds other code, and back at a step with no moves applied the change is reloaded at once as one undo step.
   - A reload at step 0 that changes the code invalidates every move whose `position`/`find` no longer matches: those moves are listed as `(stale)` in `scene.list` and skipped (the demo keeps going without them) until the author fixes them; nothing is deleted.

     *Implemented by t-164 (2026-10-20, Luis's decisions of 2026-10-18 and 2026-10-20):* a follow reload or a paste (at a step where no patch of that file is applied) is a change the demo **did not write**: it does not say where each line went, as a `move.add`/`move.delete` does (rule 3d), so a move follows it only where that is exact, with no diff and no fuzzy match. The old and the new step-0 code of the file share a start and an end (compared line by line, with the reload's own line reading, so CRLF and a final newline change nothing); a line there is the same line, the end moved by as many lines as the change added or removed. A move's line numbers (`position`, a `cursor` line, a `select` by line) get the new numbers when every line they name is there (lines written by earlier moves keep their identity through the replay, as in rule 3d), and must still hold the same text; the lines between the start and the end are the change. The rule underneath, for every case: **if the place of a line is ambiguous, the move is stale**. Under the reading of the change as the smallest one (one block, or several edits that share lines), one of several equal lines is never picked. Histories that are not the smallest and leave the same text in the same place cannot be told apart from text alone: `---`, `old`, `---` → `---`, `new`, `---` with a move on L1 reads as «line 2 changed», but if the first two lines were in fact deleted and `new`, `---` appended, the move lands on the other `---`. They need files with the same text at both ends; in documents edited while Tiza is open, prefer `find` to `position`. Decided by Luis (2026-10-20): deleting a block identical to its neighbour leaves the move on the copy that survives, without a mark, while the symmetric paste marks it — the rule is never to choose between equal lines of the **new** code, and after a deletion only one candidate with that text is left. Closing Tiza with stale moves is refused like closing with unsaved changes (`:q`, `:wq`, `q` name them and say what the next load does; `:q!` and Ctrl-C quit anyway, and print on stderr what the next load does with them): the marks are not saved in the `.tiza`. So a line of the common start or end next to the change whose text the new lines of the change repeat might be either copy, and it and every line closer to the change have no known place (the start and end are cut back to the first line whose text the change does not repeat: a function pasted next to a copy of itself, braces pasted beside a `}`). The cost, accepted: a move on the last `}` goes stale when a function is appended after it. When its old and new lines share no line it is one block: the end is shifted exactly, and a block of as many lines as before maps line for line. When they share a line there were several edits (or lines moved), the common end may be a coincidence (one `}` alike after edits further up), and every target **from the change down is stale even when the text there looks the same**, since its shift is not known; never applied in silence on a line whose shift is unknown. A move already stale follows the change the same way and is checked where its lines went; code put back exactly as it was when the move last matched (a checkout, a stash, the editor's undo) gives the move back with the numbers it had then. Without a change of code to follow (`scene.put`, `move.add`, `move.delete`), a stale move on line numbers stays stale. So a block pasted above a `replace position "3"` on a `}` shifts it to its own brace, not to the pasted block's. A text target (`find`, `after`, `before`, `select`, `rebind`) is stale when it matches nothing or more than once (or fewer times than its `occurrence`); a `wait` never. Moves are checked in the order they run, without the stale ones, so a move whose target a stale one wrote is stale too, with its own reason. An annotation on a line a stale patch writes is hidden as `(unanchored)`, kept as it was, never re-anchored onto other text; when the patch matches again it goes back on what the patch writes (shifted as far as that moved) or stays hidden if it does not fit there. A stale move keeps its numbers and the text they held, so a later change that puts that text back (or `u`, a `scene.put`, a move added or deleted) clears the mark (`move #N matches the code again`). The mark is the instance's: it is in the undo history with the moves, never in the `.tiza` (a stale move is saved as it was written, except for the exact shift of its lines when that is known; a move, stale or not, that followed its lines is saved with the new numbers); `scene.get` sends the marks beside the document, so live exports skip what the screen skips and a `scene.put` of that copy keeps each mark on its move. Known limit: a fresh load has no old text to compare, so a move by line numbers that was stale applies on the lines now there (a text target that matches nothing is still a load error); the live `check` lists every stale move — run it before closing Tiza — and in documents that read their code by reference `find` is the safer target. The bar names the stale moves once per change; `move.list`/`list_moves` carry `stale` and `stale_reason`, `status` `stale_moves`.
   - `code.link` switches the followed file: follow (if on) now watches the linked file and its parent directory, with the same pause rule while later moves are applied. Linking back (`code.link` to the original file at a later step, or `p` past the link) restores the previous watch.
   - `--follow` on the command line with a document that has moves starts at step 0 with follow active; moving forward pauses it as above. An agent that wants both live edits and a scripted demo should use `code.patch` with `find` targets (not line numbers), which survive the author's own edits better, and keep follow off during the take.

## Consequences

- The TUI gets a small animation loop (typing); any key press finishes it instantly; `u` cancels it first.
- `Document` gains `moves`, `steps`, `loop`, `views` (and every `Annotation` an optional `file`); `History` snapshots must include the applied-moves state so undo is consistent.
- Every move with a text target validates at load time (exactly one match in the code at its step); `scene.list` shows `(unanchored)` annotations and `(stale)` moves so an author sees what a patch broke without opening the JSON.
- Implementation order, by board card (reconciled 2026-10-17): **t-097** range markers `find_start`/`find_end` kept on the annotation (done) → **t-098** `moves` model + schema + load-time validation, `code.patch` apply/revert with the deterministic shift, `rebind`, `(unanchored)`, typing modes, `occurrence` (done) → **t-105** the other actions: `cursor`, `select`, `wait`, `code.link` with the per-file annotation model of rule 3f, `views` in the file, `:link path[:A-B]` at a step (done) → **t-099** named steps with `step: N`, `goto`, `auto_advance_ms`, `loop` → **t-101** `codedraw check` and `render --all-steps` applying moves → **t-106** (milestone `later`) follow mode while moves are applied (pause/resume, `code.link` switches the watch; until it lands, `follow.set` refuses to turn on while moves are applied). The `(stale)` moves of a reload or paste at a step with no move applied came first, with t-164 (§7). Discarded (2026-10-17, won't do): presenter notes, annotation templates, terminal moves, a separate preflight/recording card.
- Export (`render --step N`, `export_image`, future `--all-steps`) applies moves without animation.
- Agents can author a full demo through MCP: annotations + moves, then `goto_step` to drive it.
- Out of scope for good: slides/markdown previews, Copilot/polls/QR, OS desktop actions, editor zoom, presenter notes and presenter view, timer, clicker/remote control, snippets, terminal actions.
