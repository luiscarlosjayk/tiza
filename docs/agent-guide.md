# Agent guide

This page is for an agent (Claude Code, Zed, any MCP client) that is going to draw on the code a presenter has open in Tiza.

## Mental model

- The **TUI is the sole owner of the document**. You talk to it; you do not edit the `.tiza` by hand while it is open.
- A document has **code** (numbered lines, absolute numbering even when a range is opened) and **annotations**. Each annotation has a short, stable **id** (`a1`, `a2`… or the one you pass) and a **step** (1-based). Annotations with `step <= current step` are shown.
- **Anchors** are positions in the text: `{line, col}` or, better, `{find: "exact text", line?: N, occurrence?: K}`. `find` searches for the text on the given line (if you pass one) and then in the whole document. If it does not exist, the tool fails with `text_not_found`: do not guess columns.

## Recommended flow

1. `status` — confirm there is an instance and look at `cols`/`rows` and `warnings` (`small terminal …: labels go under the lines` → keep labels short; `code clipped (N cols)` → the presenter should widen the terminal or open a narrower range); and `redact_alerts`, which must be `[]` before anything is recorded — see «While the presenter edits»).
2. `get_code` — read the code with line numbers. Pick exact texts.
3. Annotate in the order of the explanation, assigning an increasing `step`:
   - `add_box {find_start, find_end}` (also `add_callout`, `add_spotlight`): two texts that delimit the range instead of line numbers — a comment marker (`// begin` … `// end`) or code (`fn takes` … `println`). The start is the first occurrence in the file, the end the first occurrence after it; a marker is plain text, so choose one that appears only where you mean it (the first `}` after `fn takes` may be inside a `println!("{s}")`). Errors name the missing marker. The markers are kept on the annotation (`markers`), so a later code change can re-resolve the range.
   - `add_mark` for semantic marks. Built-in, language-agnostic kinds: `info`, `warn`, `error`, `ok`, `question`, `important`, `read`, `write`, `move`, `new`, `drop`, `scope`, `flow`, `todo` (Rust habits work as aliases: `borrow`→`read`, `borrow_mut`→`write`, `lifetime`→`scope`). Each shows glyph + legend; `label` is appended. For something the author will reuse, `define_style` once (`{name, glyph, legend, color}`) and then use `name` as `kind`; for a one-off, pass `style: {glyph, legend, color}` inline. Emoji are allowed as glyphs. `list_kinds` shows what exists.
   - `add_arrow` for relationships (from where a value is born to where it is consumed). Style is the author's: `stroke` solid | dashed | dotted | thick | double, `route` rounded | sharp (a cell grid has no curves: rounded corners are the "curved" arrow), `head_start` / `head_end` none | arrow | dot | bar | open (default none → arrow; none + none is a plain connector). A convention that reads well: solid for a move, dashed for a shared borrow, thick for a mutable borrow. `update_annotation` changes them later (`stroke`, `route`, `head_start`, `head_end`); where a stub crosses another arrow's rail it breaks for one cell (the arrow passes under the rail); a box border is crossed with a junction glyph (┼ ╂ ╋ ╫ …).
   - `add_box` to delimit a function or a block. Boxes and callouts take `border` (solid | dashed | dotted | thick | double), `corners` (rounded | sharp) and `fill` (boxes are tinted by default, callouts are not); `update_annotation` changes them later.
   - `add_note` for a short sentence (one line, in the margin); `add_callout` for a paragraph of two or three sentences about a range of lines: it is a bordered block with an optional `title`, it does not displace the other labels, and `placement` is `margin` (default), `below` (own rows under `to_line`; inside a box only when the box contains the callout's whole range, otherwise after the box's bottom border) or `auto`. Use `add_box` when you want to *delimit* code, `add_note` to tag a line, `add_callout` to *explain*; `highlight` for a fragment without semantics.
   - `add_spotlight` for a "look here" step: dims the code outside `from_line..to_line` and/or the annotations outside `ids` (and focuses the code of those annotations). It draws nothing; it directs attention. Active from `step` to `until`.
4. `set_step 0` leaves only the code (a good starting point for the take); then `next_step` as the presenter advances (or leave it in their hands: `n`/`p`). A document with named steps (below) also takes `goto_step {"id": "borrow"}`.
5. `check` before you show the document (or hand it back): the same preflight as `tiza check --json` on the live document. Errors are an anchor or marker that matches nothing, a move whose target does not match exactly once at its step, a linked file that cannot be read, an unknown or duplicate id; warnings are a redact a move widens or drops (the bar's own text), an annotation hidden as `(unanchored)` at some step, a label clipped with «…» at `width` (default 100, as `tiza render`; each one names its step, id and full text) and a step with nothing new. `min_clean_width` is the narrowest width from which no label is clipped: export at that width, or shorten the labels it names (`narrower`, when present, lists the narrower widths that are clean too, with the notes under the lines). A marker that matches more than once is a warning with its lines: the range takes the first match, so make it unique. The check runs inside the instance on the real code and linked files (never on the masked copy `get_scene` gives you), so its spans and its answer are the same as `tiza check --json` on the saved file. Fix every error; warnings are the presenter's call. It reads only, and never quotes text under a redact (a target or marker on a document with redacts reads `«…»`, a marker under a mask answers exactly like one that is not there, a clipped label under a mask is named without its text).
6. `render_text` to see exactly what the audience sees and fix things. `export_image` with a `.png` or `.svg` path saves the scene as an image (fonts embedded; `step`, `width`, `theme`, `scale` optional) for thumbnails and docs; with a `.txt`, `.ansi` or `.md` path it writes the same scene as text (`.md` is a fenced block ready for a README, an issue or a chat message); with a `.gif` path it records every step of the document as an animated GIF drawn by Tiza itself (`interval` seconds per step, `skip_zero`, `scale` 2 by default, as for a PNG; the reply carries `frames` and `steps`) — nothing to install, no external tool, and the masks of t-117 are in every frame. MP4 is a shell command (`tiza render --out demo.mp4`, needs the presenter's ffmpeg), not a tool.

## Example (ownership)

```json
{"name":"add_mark","arguments":{"kind":"move","at":{"line":3,"find":"s"},"label":"s moves into takes","step":1}}
{"name":"add_arrow","arguments":{"from":{"line":2,"find":"s"},"to":{"line":15,"find":"s: String"},"label":"move","step":1,"color":"orange"}}
{"name":"add_arrow","arguments":{"from":{"line":7,"find":"&t"},"to":{"line":19,"find":"s: &String"},"label":"shared borrow","stroke":"dashed","step":3}}
{"name":"update_annotation","arguments":{"id":"a2","stroke":"thick","head_end":"bar"}}
{"name":"add_note","arguments":{"line":4,"text":"s no longer owns it: using it here does not compile","step":2}}
{"name":"add_box","arguments":{"from_line":15,"to_line":17,"label":"takes owns s and frees it at the end","step":2}}
{"name":"add_callout","arguments":{"from_line":15,"to_line":25,"title":"three ways to pass a value","text":"takes(s) moves the String. len(&s) borrows it read-only. push(&mut s) borrows it mutably.","placement":"auto","step":3,"color":"cyan"}}
```

## Emphasis

`highlight` and `add_mark` take `emphasis`: `fill` (the default tint), `underline` (a thin ‾ row under the span, good for "look here" without hiding the syntax colors), `brackets` (⌈ ⌉ beside the span; a side glued to other text goes to the row below, code is never covered) and `strike` (struck through, for "this line is gone"). The emphasis glyphs and the struck text are drawn in a softened shade of the annotation's colour (the span's own text keeps the full colour for underline and brackets), so they point without shouting; struck text still reads at the 4.5:1 code contrast. `update_annotation {"id", "emphasis": "strike"}` changes it later. Omitted means fill, and fill is not written to the file.

## Color

Every annotation accepts `color`: `orange`, `blue`, `green`, `purple`, `pink`, `cyan`, `yellow`, `red`, `gray` (Spanish aliases such as `azul`, `verde`… also work) or `#rrggbb`. Use it to tell a story per value: everything that happens to `s` in one color, everything about `t` in another. Arrows without a color rotate through an automatic palette; boxes, notes and highlights without a color use the theme's. `update_annotation` with `color: ""` returns to automatic.

## Fixing a misplaced annotation

`update_annotation` moves an annotation without recreating it, so it keeps its id, kind, style, label, color and place in the list: `at` for highlights, marks and notes (`{"id": "a1", "at": {"line": 15, "find": "s: String"}}`), `from`/`to` for arrows, `from_line`/`to_line` for boxes, callouts, spotlights and notes. A field that does not apply to the annotation's type fails with `invalid_argument` (e.g. `from_line` on a mark), and unknown fields are rejected, so a call that returns a new revision did change something. Over the socket the same goes under `move`: `annotation.update {"id": "a1", "move": {"at": {...}}}`.

## Is it on screen?

`annotation.add` and `annotation.update` (and every MCP `add_*`, `highlight`, `redact` and `update_annotation`) reply with where the annotation stands against the view at the moment it is applied (t-155): `{"id": "a17", "revision": 42, "step": 1, "shown_step": 0, "visible": false, "hidden": "it appears at step 1"}`. `step` is the annotation's step (a new one at step 0 still goes to step 1, and the view stays at 0), `step_title` is added when that step is named, `shown_step` is the step the view was showing, and `visible` says whether it is drawn there. When it is not, `hidden` says why in words: `it appears at step 3`, `its file src/queue.rs is not shown at step 2 (main.rs is)` (a `code.link` shows another file at that step), `its lines are outside the code shown at step 2 (10-36)` (outside the link's window), `it lost its anchor at step 2 (unanchored: …)`, `a spotlight shows only at its step 1`, or, with `redact_from_step`, `it masks from step 3`. The MCP tools put it in one sentence before the JSON: `a17 added at step 1; not visible now: the view is at step 0 and it appears at step 1 (next_step shows it).` A hidden annotation is not an error: say so to the presenter instead of adding it again, and do not move their view yourself unless they asked. The presenter is told too: their status bar says `a17: box 3-5 added by agent (step 1, press n)` (several of yours within a second share one message, `3 agent annotations not shown (step 1, press n)`; in presentation mode it waits until they leave it), so there is no need to repeat it in the chat unless they ask. In supervised mode the reply is computed when the presenter accepts the proposal, so `shown_step` is the step on screen at that moment, which may not be the one you saw when you asked; the view can move again right after, so read `visible` as a snapshot. `annotation.delete` still replies `{id, revision}`.

## Pointing live

`point_at` (socket `pointer.set`) is a laser pointer on the presenter's screen (t-030): the line you name stays as it is and the rest of the code dims while you talk about it. Give `{"line": 7}`, `{"line": 7, "find": "takes(s)"}` (the text must be on that line), `{"find": "takes(s)"}` (it must appear once in the code shown; otherwise `invalid_argument` lists the lines) or `{"from": 15, "to": 17}`. The view scrolls to it and the presenter's cursor moves there, so their `j`/`k` go on from your line. `clear_pointer` (`pointer.clear`) turns it off. It is the same pointer as the presenter's `f` key: the last one wins — when the presenter moves the cursor the pointer follows them (`status.pointer.by` goes from `agent` to `presenter`), and `f` turns yours off. `status` carries `pointer` (`{"line": 7, "to": 7, "by": "agent"}`) or `null`. The reply's `shown` is `false` while the presenter has the command line open: it shows when they close it. On `n`/`p` it stays on its line (carried through the moves of the step) and goes off when that line disappears.

Point instead of adding a spotlight when the focus is for this moment of the conversation, not for the recording: the pointer creates nothing — no annotation, no revision, no undo entry, no autosave — and no export, GIF, `.cast`, `.tape`, MP4 or `render_text` draws it. Use `add_spotlight` when the focus belongs to a step and must be in the take. A `find` is searched on the masked code, like everywhere else: a redacted value is never found, and the pointer never uncovers a mask.

## Between takes

`clear_annotations` empties the canvas at once (or only one step with `step`). The presenter can undo it with `u`, so it is not destructive live.

## While the presenter edits

`set_follow {"enabled": true}` makes the TUI reload the code every time the source file is saved (the presenter can also type `:follow on`). Annotations stay anchored to their text; the ones whose text disappears are dropped, and the reply (same as `follow.status`) reports `reloads` and `last_reload`, so after a save you can call `list_annotations` to see what survived and re-add what matters. It fails with `invalid_argument` when the code is embedded in the document.

A reload, a paste or a move can widen or drop a redact (or retarget a later move); the TUI then shows a loud notice on rows of its own above the bar until the presenter presses a key, and `status` carries the same notices in `redact_alerts` (t-156), oldest first, ids, lines and visible text only — never what a mask covers: `["redact a1 could not follow its text: masking the rest of L4 — fix it before recording (u undoes the reload)"]`. A later reload does not clear them (its own message goes to the bar; these stay). While `redact_alerts` is not empty, do not start a take: tell the presenter to look at the screen, read `get_code`, and re-mark the value (a new `redact` over it) or fix the move. It goes back to `[]` when the presenter presses a key in the TUI; nothing you send clears it.

## Code that changes between steps (moves)

When the lesson adds or rewrites code as it goes, do not open a second document: add a **move**. `add_move {at_step, op: insert|replace|delete, …, content, typing?, speed_ms?, rebind?}` registers a `code.patch` the TUI applies when the presenter reaches `at_step` and reverts when they go back; `render --step N` and the exports apply it instantly. Targets are matched on the code **as shown at that step** (after the moves of earlier steps and the earlier moves of the same step) and must match exactly once: `after`/`before` the text of a line or `position` (the line the content goes before; last+1 appends) for an insert; `find`, `find_start`/`find_end` or `position: "7-9"` for a replace or delete. When the text appears more than once, say which one with `occurrence: N` — 1-based, counted in reading order over the **whole** code at that step, a line holding the text twice counting twice (`end_occurrence` for `find_end`); an N past the last match is an error naming the move, and so is an ambiguous target without it. `get_code` at that step shows you the matches. `typing: "line"` or `"char"` types the content in place (`speed_ms` per unit, 120 / 25 by default).

Annotate the new code **at the step where it exists**: after `add_move {at_step: 2, …}`, an `add_note {step: 2, line: 7}` is validated on the step-2 code, whatever step the TUI is showing. Annotations of earlier steps are shifted through the patch by the patch itself (lines after an insert or delete move, a range shrinks to its surviving lines). On a line a `replace` overwrites, notes, boxes, callouts and spotlights keep the line at the same offset, but **highlights, marks and arrow ends lose their anchor** (the text under their columns is gone) and are hidden as `(unanchored)` in `list_annotations` — never deleted — unless your move names where they go: `rebind: {"a4": {"at": {"find": "t.len()", "occurrence": 1}}}` (the same fields as `update_annotation`, resolved on the code after the patch; a `find` there must match exactly once or carry `occurrence`, checked when the move is added; a spec with none of `at`, `from`/`to` or `from_line`/`to_line`, or with an unknown key, is rejected). The same goes for any annotation that loses every line. `list_moves` shows every move with its index and the ids currently unanchored; `delete_move {index}` removes one. Paste and follow are refused while a move is applied (step 0 first).

## Showing another file (views)

To move between **files** during the demo, each with its own annotations, add a `code.link` move: `add_move {at_step: 2, action: "code.link", file: "src/queue.rs", lines: "10-36"}` shows `src/queue.rs` (a path as `code.file` would name it, relative to the `.tiza`; the TUI reads it next to the document) from step 2 on, until a later link shows another file or the main one again (`file` naming the document's own file links back; nothing else is needed). `lines` is **only a window**: it crops what is shown, every annotation keeps the file's real line numbers, and the same file with another window is the same view. Annotations belong to a file: an `add_box {step: 2, …}` at a step that shows `queue.rs` is a box **of `queue.rs`** (it gets `"file": "src/queue.rs"`; you may also pass `file` to `annotation.add` yourself), it is validated on that file's code at that step, and `list_annotations` ends its line with the file in parentheses (`a4 [step 2] box L17-23 «FIFO» (src/queue.rs)`; the main file's annotations carry no suffix). While a file is shown the others' annotations are not drawn — they are not `(unanchored)`, and they come back untouched when the demo links back. Likewise a note outside the window is kept, not drawn. `get_code` returns the file shown at the current step, cropped to its window, with a first line `# src/queue.rs:10-36` naming it; `status` carries `file`, `view`, `first_line` and `last_line`. A `code.patch` edits the file shown at its step (its targets are matched there). The saved `.tiza` references the linked files by path; `:embed` (or `scene.get`, which always embeds) stores a copy of each under `views`. A link to a file that cannot be read is an error naming the move and the path.

Three small moves complete the set: `add_move {action: "cursor", line, col?}` puts the cursor on a line of the shown file, `{action: "select", from: {find: "&mut u"}, to: {find: "u);"}}` highlights from the start of the first text to the end of the second (each `find` must match exactly once at that step, or carry `occurrence`; `{line, col}` works too), and `{action: "wait", ms}` pauses before the step's annotations appear (TUI, GIF and tape; a still render ignores it). A `code.link` clears the cursor and the selection; `render --step N` draws both.

## Named steps, auto-advance and loop

A `.tiza` may name steps (t-099, ADR 0007 §4): `"steps": [{"step": 3, "id": "borrow", "title": "Shared borrow", "auto_advance_ms": 3000}]`, plus `"loop": true`. The number, not the place in the list, binds an entry to its step, so moving annotations between steps never shifts a title; entries are sparse and saved sorted by `step`; ids are unique, one word, never all digits (a number always means a step number) and never start with `-`; a bad id fails with `invalid_argument`. Only `step`, `id`, `title` and `auto_advance_ms` are known: any other key in an entry is kept but warned about in `status.warnings`. Set them with `scene.patch {"steps": [...], "loop": true}` (the whole list is replaced; `[]` clears it) or in the document you `scene.put`; `scene.get` returns them.

- `goto_step {"id": "borrow"}` (socket `step.goto`; both also take a step number, `{"id": 3}` or `{"id": "3"}`) lands on that step exactly as `next_step` would after walking from step 0: the code recomputed with every move up to it, linked files and redacts included, and a typed step complete (no animation). An unknown id fails with `not_found` and the message lists the named ones; a value that is neither (`-1`, `4.5`, `null`) is `invalid_argument` ("`id` must be a step id or a step number from 0 to N"). The reply of every `step.*` call carries `id`, `title` and `label` (`step 3/7 · Shared borrow`).
- `status` reports `step_id`, `step_title`, `step_label`, the current step's `auto_advance_ms` and `loop`; `list_annotations` starts with a `# step 3/7 · Shared borrow` line. An entry for a step past the last one is kept and listed in `status.warnings`.
- With `auto_advance_ms` the TUI goes to the next step on its own that long after the step is ready (typing finished, `wait` moves elapsed); it waits while the presenter has the `:` line, a `v`/`V` selection or an overlay open. With `loop: true`, `next_step` (and an auto-advance) past the last step is step 0. The native GIF/MP4 hold such a step for its `auto_advance_ms` instead of `--interval`.
- Scripts and editor tasks use the CLI, no JSON: `tiza next`, `tiza prev`, `tiza goto borrow` (session socket, or `--socket`/`--session`); they print the step reached and exit non-zero when no instance listens.

This is automation (recordings, a looping booth screen, an editor task), not speaker tooling: there are no presenter notes and no timer.

## Supervised mode

**Themes.** `set_theme` takes `dark`, `light`, `terminal` (the host's palette), `auto` (follow the terminal's background) or `toggle`; the reply says whether the instance is following (`auto`). A document may carry `theme_overrides` (per-token colours); `export_image` applies them and, for a terminal theme, paints the matching dark/light palette instead — there is no host palette in a file.

**The margin is the presenter's too.** `status.margin` is the cap on the right margin when one is set (`scene.patch {"margin": 24}` sets it, `null` removes it); long notes wrap at it. Keep notes short either way — a wrapped note takes rows from the lines below it.

**The gutter is the presenter's.** `status.numbers` says whether line numbers are shown; `scene.patch {"numbers": false}` hides them (saved in the document, so every export follows). Line numbers in your anchors (`line`, `find`) are the real ones whatever the gutter shows.

**One geometry per take.** `render_text` and `export_image` size the arrow lanes, the box band and the margin for the maximum over every step of the document (t-111), the same way presentation mode does: a frame at step 1 and one at step 7 put the code at the same x, so you can compare frames and build thumbnails that line up. The presenter's authoring screen may look narrower than your render at an early step; that is the dynamic layout, not a bug, and `:layout stable` on their side makes the two agree.

**Secrets on screen.** The presenter may mask a span with a `redact` annotation (or ask you to: `redact {at: {line, find: "API_KEY="}}` masks what follows the anchor; `{at: {line, col, end}}` masks columns; `keep` shows the last characters). The mask is applied in one place, at the layout boundary, so what you read is what the viewer sees: `get_code`, `scene.get`, `render_text`, the `tiza://` resources and every export return eight `•` where the secret is, and a `find` on a masked substring fails like text that is not there — do not try to read around a mask, and never put a secret into a `find` or a label (a `find` that looks like a secret is refused). `list_annotations` shows `redact L2 (masked)` with columns only. When the code reloads (follow, paste) a redact follows the text around it, not the secret, so a rotated value stays masked; one that cannot follow its text fails closed: while its line is there the mask widens to the rest of the line (or to every line of an edit that changed size) with no kept tail, the annotation carries `"widened": true` in `scene.get` and `WIDENED` in `list_annotations`, and only a redact whose line was deleted with nothing in its place is dropped (with a notice). A widened mask is cleared by marking the value again: a new `redact` over it replaces it. Check `get_code` after a reload rather than assuming, and never try to read what a widened mask covers. Moves follow the same fail-closed rule (t-140): a `code.patch` that rewrites a redacted line carries the mask with the value or widens it (`WIDENED` at that step in `list_annotations`, `"widened": true` in `scene.get` while that step is shown), on every typed frame too; move content comes back masked in `scene.get`, `list_moves` and `tiza://scene` (eight `•` wherever it lands under a mask), and `add_move` with content that repeats a masked value where no mask would cover it fails with `invalid_argument` — do not copy a masked value into a move; write the new value in place of the masked one. A `position` target counts lines of the code at its step, so a move you add at an earlier step can retarget a later one (t-157): `add_move`/`delete_move` then return a notice per retargeted move (`move #1, step 2 now replaces L2 «# config» instead of «token=…»: check it`) — read `get_code` at that step and fix the target (prefer `find`/`after` on visible text). Any copy of a masked value in a line a move writes, whole or a piece of 4+ of its characters, is masked as its whole token (the rest of the line when the token ends at `=` or `:`), with `WIDENED`. A redact's `step` may read 0: it says which code its columns refer to (the untouched file), not when it shows — masks are on from step 0. A redact on a line a move wrote carries `"pin": N` (t-154): its columns refer to the code right after move #N, and Tiza keeps it on that line when moves are added or deleted before it (`delete_move` of move #N drops it and says so in `notices`); with `redact_from_step` its `step` is when it shows and `"pin": 0` says its columns are on the file. Send `pin` back as you got it (`scene.get` → `scene.patch`/`scene.put`) or leave it out on a redact you add (Tiza pins it). When you write a document with redacts and moves yourself, give each redact `"step": 0` with columns on the file; a redact without `pin` whose step has a move on its line is read both ways (masked on the file and on the code after the move), which may mask more than you meant. In a move's targets (`find`, `after`, `before`, `find_start`, `find_end`, `select`/`rebind` `find`) never put a secret: one that looks like a secret is refused with `invalid_argument`, and one under a mask is not found (`text_not_found`, the text not repeated) — target the line by `position` or by the visible text before the value. On a document with any redact no error repeats a target you wrote (t-167): `find`, `at.find`, markers, `after`/`before`, `select`/`rebind`, a step id for `goto_step` — all come back as «…» (`text "…" not found in the code`, or for a move `move #2, step 3: find «…» matches nothing in the code at this step`), under the mask or not, so the answer never says whether your text was under one; supervised-mode summaries quote no `find` either. A value outside a fixed set (a color, `border`, `corners`, `stroke`, `route`, a head, `emphasis`, `placement`, a mark `kind`, `theme`, a move's `action`/`op`/`typing`/`position`, a method name) is never repeated, redact or not: the error lists the valid names (`unknown border (use solid, dashed, …)`, `invalid parameters: unknown variant «…», expected one of …`). Neither is the name of a field that is not one (`unknown field «…», expected …`); on a document with redacts the keys and numbers you sent are not repeated either (`move #… does not exist`). Keep your own copy of what you sent.

**What stays local.** Everything you send over the socket or the MCP stays on this machine: the `tiza` binary has no network dependencies and never opens a connection (README «What Tiza reads and writes», [ADR 0009](adr/0009-politica-de-red.md)). Your `add_note`, the code you read with `get_code`, the exports you request — none of it leaves the presenter's computer unless *they* run a separate `tiza-net` command on purpose. Do not expect a `publish` or an `upload` tool here, and do not try to reach the network on Tiza's behalf: if the presenter wants a GIF on a service, produce the file locally and tell them which command would send it.

**Saving rule.** The TUI writes every change to the `.tiza` sidecar of the file that is open — your `add_note` lands on disk at once — unless the presenter opened it with `--no-save` or turned `:autosave off` (`status.autosave` tells you; `:w` is theirs), or the sidecar cannot be written (a read-only file or folder: the presenter is told once, the bar shows `read-only • unsaved (:w)`, your calls keep succeeding in memory and `:q` refuses until they `:w PATH` or `:q!`; the next autosave that works clears it). `scene.put` of a document from **another source** (a different `source.path`, or embedded code with none) is shown but never autosaved over the file that was open: autosave stops with a message, and the presenter decides with `:w` (over the open file), `:w PATH` (elsewhere) or `:autosave on` (resume). A put of the same source — re-putting an edited copy of the open document, `scene get` → `scene put` — keeps saving as before. `u` after a put brings the previous document back, step included. From the CLI, `tiza scene put FILE` takes a `.tiza` or the `scene get` envelope and refuses anything else unless `--as-code` is passed.

The presenter may turn on `:supervise`: then every mutating call (add, update, delete, clear, step, theme, focus, pointer, follow, scene put/patch) waits until they press `y` or `n` in the TUI. Accepted calls return their normal result (for an annotation, `visible` and `shown_step` as of the acceptance); rejected ones fail with code `rejected` ("the presenter rejected this change"), and so does a proposal left undecided for 60 s. `status` tells you (`supervised`, `pending`). Do not retry a rejected change in a loop; say what you wanted to draw and let the presenter answer. Reads never wait.

## Resources

If your client supports MCP resources, `tiza://scene`, `tiza://code`, `tiza://render` and `tiza://render.md` are always readable (no caching: every read reflects the live instance). They are the same views as `get_code` / `render_text` / `scene.get`; use whichever your client makes cheaper to attach as context.

`tiza://scene` is a reader's copy (t-174): any text that repeats a masked value — a label, a note, a callout, a step title, the document title — comes masked (`was ••••••••`), as on screen, because a client may attach a resource to your context on its own and nothing is written back from it. The socket's `scene.get` (`tiza scene get`) is the editing call: it returns the author's text as written (the code under a redact is masked either way); `scene.get {"as_shown": true}` gives the reader's copy. So edit from `scene.get`, never from `tiza://scene`: a document rebuilt from the resource and sent back with `scene.put` would write the bullets into the labels. If a text you write (a label, a note, a title, a style's legend or glyph) shares four characters in a row with a masked value, it is accepted but masked everywhere, and the reply says `"masked": true` with `masked_notice` (`a3: its label shares text with a masked value; masked on screen — reword the label`); the presenter sees the same alert and `check` warns (`masked_text`). An id you choose that shares text with a masked value is refused (`invalid_argument`, the id not repeated). Write labels and ids that do not repeat what a redact hides; reword when told. After `scene.put` of what `scene.get` gave you the instance still masks those texts (it keeps the values it knew, in memory only). When the document's code is embedded, Tiza saves those texts masked in the `.tiza` (and the content of moves as it is shown), so once it has written the file the alert reads `… saved masked — reword it`: the author's wording is lost in the file, so reword rather than wait for it. Before the first write it reads `… demo.tiza still holds it in clear — open and save it in Tiza, or reword it`, and `check` adds a `clear_value` warning when the embedded code itself holds a masked value in clear. A text that already holds `••••••••` (one Tiza saved masked) is said too: `a3: its label holds masked text — reword it`. Matching ignores case: `HUNTER2` is a copy of `hunter2`. A document whose code is a file reference stays one through `scene.get` → `scene.put`: put back what you got (edited or not) and the instance puts it on its file again, with the real columns; an annotation you moved on the masked copy is mapped to the real code. File names are document text too: `status.file`/`status.view` and `get_code`'s header come masked when a name shares text with a masked value.

## Idempotency

Pass your own `id` (`"id": "move-s"`) so that a retry does not duplicate the annotation: the second attempt fails with `duplicate_id` and you can move on.

## After a rebuild

`status` returns a `bridge` object: `version`, `build` (git commit of this MCP server) and, when the `tiza` binary on disk is newer than the running server, `binary_rebuilt: true` plus a `hint`. That means the tool list you hold may be stale: tell the user to reconnect the server (Claude Code: `/mcp` → tiza → reconnect) before relying on a tool you cannot see. `instance_build` appears when the TUI was built from a different commit than the bridge: ask the user to restart the TUI as well.

## Schema

`tiza schema document` and `tiza schema api` print the JSON Schemas (also committed under `schema/`); the live instance answers `api.schema` with the params and result of every method, so a client can validate what it sends. Agents without a terminal can pipe documents: `tiza render - --out shot.png < demo.tiza`.

## Without MCP: socket and CLI

Same contract, one JSON request per line over the Unix socket:

```sh
printf '%s\n' '{"id":1,"method":"annotation.add","params":{"type":"note","line":4,"text":"hello"}}' | nc -U "$TMPDIR/tiza/default.sock"
tiza api annotation.add '{"type":"note","line":4,"text":"hello"}'
tiza api api.methods
tiza check demo.tiza --json   # preflight of a file, no instance needed (exit 1 on errors)
```

Response: `{"id":1,"result":{...}}` or `{"id":1,"error":{"code":"text_not_found","message":"..."}}`. Codes: `out_of_range`, `not_found`, `duplicate_id`, `text_not_found`, `invalid_argument`, `invalid_json`, `unavailable`.
