# Agent guide

This page is for an agent (Claude Code, Zed, any MCP client) that is going to draw on the code a presenter has open in Tiza.

## Mental model

- The **TUI is the sole owner of the document**. You talk to it; you do not edit the `.tiza` by hand while it is open.
- A document has **code** (numbered lines, absolute numbering even when a range is opened) and **annotations**. Each annotation has a short, stable **id** (`a1`, `a2`… or the one you pass) and a **step** (1-based). Annotations with `step <= current step` are shown.
- **Anchors** are positions in the text: `{line, col}` or, better, `{find: "exact text", line?: N, occurrence?: K}`. `find` searches for the text on the given line (if you pass one) and then in the whole document. If it does not exist, the tool fails with `text_not_found`: do not guess columns.

## Recommended flow

1. `status` — confirm there is an instance and look at `cols`/`rows` and `warnings` (`small terminal …: labels go under the lines` → keep labels short; `code clipped (N cols)` → the presenter should widen the terminal or open a narrower range).
2. `get_code` — read the code with line numbers. Pick exact texts.
3. Annotate in the order of the explanation, assigning an increasing `step`:
   - `add_box {find_start, find_end}` (also `add_callout`, `add_spotlight`): two texts that delimit the range instead of line numbers — a comment marker (`// begin` … `// end`) or code (`fn takes` … `println`). The start is the first occurrence in the file, the end the first occurrence after it; a marker is plain text, so choose one that appears only where you mean it (the first `}` after `fn takes` may be inside a `println!("{s}")`). Errors name the missing marker. The markers are kept on the annotation (`markers`), so a later code change can re-resolve the range.
   - `add_mark` for semantic marks. Built-in, language-agnostic kinds: `info`, `warn`, `error`, `ok`, `question`, `important`, `read`, `write`, `move`, `new`, `drop`, `scope`, `flow`, `todo` (Rust habits work as aliases: `borrow`→`read`, `borrow_mut`→`write`, `lifetime`→`scope`). Each shows glyph + legend; `label` is appended. For something the author will reuse, `define_style` once (`{name, glyph, legend, color}`) and then use `name` as `kind`; for a one-off, pass `style: {glyph, legend, color}` inline. Emoji are allowed as glyphs. `list_kinds` shows what exists.
   - `add_arrow` for relationships (from where a value is born to where it is consumed). Style is the author's: `stroke` solid | dashed | dotted | thick | double, `route` rounded | sharp (a cell grid has no curves: rounded corners are the "curved" arrow), `head_start` / `head_end` none | arrow | dot | bar | open (default none → arrow; none + none is a plain connector). A convention that reads well: solid for a move, dashed for a shared borrow, thick for a mutable borrow. `update_annotation` changes them later (`stroke`, `route`, `head_start`, `head_end`); where a stub crosses another arrow's rail it breaks for one cell (the arrow passes under the rail); a box border is crossed with a junction glyph (┼ ╂ ╋ ╫ …).
   - `add_box` to delimit a function or a block. Boxes and callouts take `border` (solid | dashed | dotted | thick | double), `corners` (rounded | sharp) and `fill` (boxes are tinted by default, callouts are not); `update_annotation` changes them later.
   - `add_note` for a short sentence (one line, in the margin); `add_callout` for a paragraph of two or three sentences about a range of lines: it is a bordered block with an optional `title`, it does not displace the other labels, and `placement` is `margin` (default), `below` (own rows under `to_line`; inside a box only when the box contains the callout's whole range, otherwise after the box's bottom border) or `auto`. Use `add_box` when you want to *delimit* code, `add_note` to tag a line, `add_callout` to *explain*; `highlight` for a fragment without semantics.
   - `add_spotlight` for a "look here" step: dims the code outside `from_line..to_line` and/or the annotations outside `ids` (and focuses the code of those annotations). It draws nothing; it directs attention. Active from `step` to `until`.
4. `set_step 0` leaves only the code (a good starting point for the take); then `next_step` as the presenter advances (or leave it in their hands: `n`/`p`). A document with named steps (below) also takes `goto_step {"id": "borrow"}`.
5. `check` before you show the document (or hand it back): the same preflight as `tiza check --json` on the live document. Errors are an anchor or marker that matches nothing, a move whose target does not match exactly once at its step, a linked file that cannot be read, an unknown or duplicate id; warnings are an annotation hidden as `(unanchored)` at some step, an annotation outside the `code.link` window of a step that shows its file (`outside_window`, from its own step on, with its lines carried there: kept, not drawn there; what the window of a later link never showed is the author zooming in and is not said, what a patch pushes out of it is), an annotation of a file its own step does not show (`not_shown`: `its file src/stack.rs is not shown at step 4 (src/queue.rs is)`, said even when that file shows at other steps, since it is never drawn at its own; one of the shown file outside the window is `outside_window` only), a label clipped with «…» at `width` (default 100, as `tiza render`; each one names its step, id and full text) and a step with nothing new. `min_clean_width` is the narrowest width from which no label is clipped: export at that width, or shorten the labels it names (`narrower`, when present, lists the narrower widths that are clean too, with the notes under the lines). A marker that matches more than once is a warning with its lines: the range takes the first match, so make it unique. The check runs inside the instance on the real code and linked files, so its spans and its answer are the same as `tiza check --json` on the saved file. Fix every error; warnings are the presenter's call. It reads only. It runs off the TUI thread, on a copy of the document, so the screen, the keys and your other calls are answered while it works (t-210); the reply adds `revision`, and the report is about exactly that revision of the document, never a mix of two. It is usually the one when you called, but a check that had to wait for another one runs on the newest copy asked for at its width, so its `revision` can be later than your call: trust `revision`, not the time you called; if a later change of yours returned a newer `revision`, check again. Checks do not stack: at most one runs and one waits. One with the same width and revision as the running one shares its run (`{}` is `{"width": 100}`); a check at another width while one already waits takes its place, and the replaced call is answered at once with `busy` (`check: replaced by a newer check (width 60) before it ran; ask again`): ask again.
6. `render_text` to see exactly what the audience sees and fix things. `export_image` with a `.png` or `.svg` path saves the scene as an image (fonts embedded; `step`, `width`, `theme`, `scale` optional) for thumbnails and docs; with a `.txt`, `.ansi` or `.md` path it writes the same scene as text (`.md` is a fenced block ready for a README, an issue or a chat message); with a `.gif` path it records every step of the document as an animated GIF drawn by Tiza itself (`interval` seconds per step, `skip_zero`, `scale` 2 by default, as for a PNG; the reply carries `frames` and `steps`) — nothing to install, no external tool. MP4 is a shell command (`tiza render --out demo.mp4`, needs the presenter's ffmpeg), not a tool. It draws the live document as the TUI has it, the files a `code.link` shows included (the instance sends them with the scene; t-166), and every call answers: with the file written or with an error, never a call left waiting. It renders off the server's own threads, so `status` and the other tools keep answering while it works; one that takes longer than 120 s is abandoned with an error saying so and writes nothing (export a still, fewer steps or a smaller scale, or ask the presenter to run `tiza render` in a terminal, which has no deadline). A `step` past the last one exports the last and the reply says so in `warning` (and `step` is the step exported); `interval` takes 0 to 3600 seconds.

## Example (ownership)

```json
{"name":"add_mark","arguments":{"kind":"move","at":{"line":3,"find":"s"},"label":"s moves into takes","step":1}}
{"name":"add_arrow","arguments":{"from":{"line":2,"find":"s"},"to":{"line":15,"find":"s: String"},"label":"move","step":1,"color":"orange"}}
{"name":"add_arrow","arguments":{"from":{"line":7,"find":"&t"},"to":{"line":19,"find":"s: &String"},"label":"shared borrow","stroke":"dashed","step":3}}
{"name":"update_annotation","arguments":{"id":"a2","stroke":"thick","head_end":"bar"}}
{"name":"add_note","arguments":{"line":4,"text":"s no longer owns it: using it here does not compile","step":2}}
{"name":"add_box","arguments":{"from_line":15,"to_line":17,"label":"takes owns s and frees it at the end","step":2}}
{"name":"add_callout","arguments":{"from_line":15,"to_line":25,"title":"three ways to pass a value","text":"takes(s) moves the String. len(&s) borrows it read-only. push(&mut s) borrows it mutably.","placement":"auto","step":3,"color":"cyan"}}
```

## Emphasis

`highlight` and `add_mark` take `emphasis`: `fill` (the default tint), `underline` (a thin ‾ row under the span, good for "look here" without hiding the syntax colors), `brackets` (⌈ ⌉ beside the span; a side glued to other text goes to the row below, code is never covered) and `strike` (struck through, for "this line is gone"). The emphasis glyphs and the struck text are drawn in a softened shade of the annotation's colour (the span's own text keeps the full colour for underline and brackets), so they point without shouting; struck text still reads at the 4.5:1 code contrast. `update_annotation {"id", "emphasis": "strike"}` changes it later. Omitted means fill, and fill is not written to the file.

## Color

Every annotation accepts `color`: `orange`, `blue`, `green`, `purple`, `pink`, `cyan`, `yellow`, `red`, `gray` (Spanish aliases such as `azul`, `verde`… also work) or `#rrggbb`. Use it to tell a story per value: everything that happens to `s` in one color, everything about `t` in another. Arrows without a color rotate through an automatic palette; boxes, notes and highlights without a color use the theme's. `update_annotation` with `color: ""` returns to automatic.

## Fixing a misplaced annotation

`update_annotation` moves an annotation without recreating it, so it keeps its id, kind, style, label, color and place in the list: `at` for highlights, marks and notes (`{"id": "a1", "at": {"line": 15, "find": "s: String"}}`), `from`/`to` for arrows, `from_line`/`to_line` for boxes, callouts, spotlights and notes. A field that does not apply to the annotation's type fails with `invalid_argument` (e.g. `from_line` on a mark), and unknown fields are rejected, so a call that returns a new revision did change something. Over the socket the same goes under `move`: `annotation.update {"id": "a1", "move": {"at": {...}}}`.

## Is it on screen?

`annotation.add` and `annotation.update` (and every MCP `add_*`, `highlight` and `update_annotation`) reply with where the annotation stands against the view at the moment it is applied (t-155): `{"id": "a17", "revision": 42, "step": 1, "shown_step": 0, "visible": false, "hidden": "it appears at step 1"}`. `step` is the annotation's step (a new one at step 0 still goes to step 1, and the view stays at 0), `step_title` is added when that step is named, `shown_step` is the step the view was showing, and `visible` says whether it is drawn there. When it is not, `hidden` says why in words: `it appears at step 3`, `its file src/queue.rs is not shown at step 2 (main.rs is)` (a `code.link` shows another file at that step), `its lines are outside the code shown at step 2 (10-36)` (outside the link's window), `it lost its anchor at step 2 (unanchored: …)`, or `a spotlight shows only at its step 1`. The MCP tools put it in one sentence before the JSON: `a17 added at step 1; not visible now: the view is at step 0 and it appears at step 1 (next_step shows it).` A hidden annotation is not an error: say so to the presenter instead of adding it again, and do not move their view yourself unless they asked. The presenter is told too: their status bar says `a17: box 3-5 added by agent (step 1, press n)` (several of yours within a second share one message, `3 agent annotations not shown (step 1, press n)`; in presentation mode it waits until they leave it), so there is no need to repeat it in the chat unless they ask. In supervised mode the reply is computed when the presenter accepts the proposal, so `shown_step` is the step on screen at that moment, which may not be the one you saw when you asked; the view can move again right after, so read `visible` as a snapshot. `annotation.delete` still replies `{id, revision}`.

## Pointing live

`point_at` (socket `pointer.set`) is a laser pointer on the presenter's screen (t-030): the line you name stays as it is and the rest of the code dims while you talk about it. Give `{"line": 7}`, `{"line": 7, "find": "takes(s)"}` (the text must be on that line), `{"find": "takes(s)"}` (it must appear once in the code shown; otherwise `invalid_argument` lists the lines) or `{"from": 15, "to": 17}`. The view scrolls to it and the presenter's cursor moves there, so their `j`/`k` go on from your line. `clear_pointer` (`pointer.clear`) turns it off. It is the same pointer as the presenter's `f` key: the last one wins — when the presenter moves the cursor the pointer follows them (`status.pointer.by` goes from `agent` to `presenter`), and `f` turns yours off. `status` carries `pointer` (`{"line": 7, "to": 7, "by": "agent"}`) or `null`. The reply's `shown` is `false` while the presenter has the command line open: it shows when they close it. On `n`/`p` it stays on its line (carried through the moves of the step) and goes off when that line disappears.

Point instead of adding a spotlight when the focus is for this moment of the conversation, not for the recording: the pointer creates nothing — no annotation, no revision, no undo entry, no autosave — and no export, GIF, `.cast`, `.tape`, MP4 or `render_text` draws it. Use `add_spotlight` when the focus belongs to a step and must be in the take.

## Between takes

`clear_annotations` empties the canvas at once (or only one step with `step`). The presenter can undo it with `u`, so it is not destructive live.

## While the presenter edits

`set_follow {"enabled": true}` makes the TUI reload the code every time the source file is saved (the presenter can also type `:follow on`). At a step with moves applied it turns on and waits: a save is not loaded there, the code on screen stays (embedded in the `.tiza` meanwhile) and the first step with no moves applied loads it as one reload; the reply's `message` and the bar say `following main.rs (waiting: moves applied at step 1; loads at step 0)`, and `follow.status` gives `enabled: true` with that `reason` (`loads at step 2 or earlier` when the first move is at step 3: a save loads at any step before the first move). Annotations stay anchored to their text; the ones whose text disappears are dropped, and the reply (same as `follow.status`) reports `reloads` and `last_reload`, so after a save you can call `list_annotations` to see what survived and re-add what matters. It fails with `invalid_argument` when the code is embedded in the document and no followed file is known (read from stdin, or frozen with `:embed`); embedded code that replaced a followed file (a paste, an undo past a reload, while `follow.status` gives that file's `path`) is not a failure: the call loads that file over it, as below. A paste by the presenter turns follow off, since the pasted code is theirs and a save must not replace it: `follow.status` then says `enabled: false` with a `reason` (`the code is pasted, not main.rs; :follow on reloads main.rs`), and `set_follow {"enabled": true}` loads the file over the paste as one reload the presenter can undo. The same happens when the presenter's `u` (or redo) brings back code the file no longer holds, such as the code from before a reload: the code stays embedded in the `.tiza`, follow turns off and `reason` says `the code on screen is not main.rs; :follow on reloads main.rs`. The `reason` always describes the code on screen now, and is absent once the file holds that code again; a `scene.get` → `scene.put` of such a document keeps the code embedded.

A reload or a paste re-anchors every annotation by its text; one whose text is gone is dropped and the presenter is told.

A reload or a paste is not written by the demo, so a move follows it only where that is exact: the old and the new code share a start and an end, those lines are the same lines (the end moved by what the change added or removed), and a move's line numbers there (`position`, a `cursor` line, a `select` by line) get the new numbers — a line pasted above a target moves it down with its text, even when other lines hold the same text. The rule underneath: **if the place of a line is ambiguous, the move is stale** — a line of the common start or end next to the change whose text the change repeats (a function pasted next to a copy of itself) has no known place. This reads the change as the smallest one: one block, or several edits that share lines. A longer history that leaves the same text in the same place cannot be told apart from text alone: `---`, `old`, `---` → `---`, `new`, `---` with a move on L1 reads as «line 2 changed», but if the first two lines were in fact deleted and `new`, `---` appended, the move lands on the other `---`. That needs a file with the same text at both ends; in documents edited while Tiza is open, prefer `find` to `position`. Deleting a block identical to its neighbour leaves the move on the copy that survives, without a mark, while pasting such a block next to it marks the move: the rule is never to choose between equal lines of the new code, and after a deletion only one is left. The change is one block when its old and new lines share no line; when they share one there were several edits, and every target from the change down is **stale** even when the text there looks the same (a target inside a one-block change is stale unless the block kept its size, line for line), and so is one whose lines no longer hold the text they held; a text target is stale when it now matches nothing or more than once, and a move whose target a stale one wrote is stale too. A stale move is skipped when stepping (the steps keep their numbers), kept in the file as written (only its line numbers follow a change whose shift is exact), and named on the presenter's bar once per change (`stale move skipped (u undoes or re-add): #1 (L2 changed)`); annotations on lines a stale patch writes are hidden as `(unanchored)`, not drawn on other text, and come back on what it writes when it matches again. `list_moves` gives `stale: true` and `stale_reason`, `list_annotations` lists the stale moves last as `move #N … (stale: why)`, `status` has `stale_moves`, and `check` reports each one. A later reload or paste that makes the move match again clears the mark (`move #1 matches the code again`), and so does `u`; code put back exactly as it was when the move last matched (a checkout, a stash, the editor's undo) gives the move back with its numbers. An `add_move`/`delete_move` or a `scene.put` re-checks only text targets: a stale move on line numbers stays stale until the code says where its lines are. The marks are the live instance's only: `scene.get` sends them next to the document (`stale`, `held`), never in it, so `export_image` skips what the screen skips and a `scene.put` of that copy keeps the same moves stale. After closing Tiza a move by line numbers whose lines changed loads and applies on the lines now there without a word (a text target that matches nothing is still a load error): **in a document that reads its code by reference (the author keeps editing the file), target moves with `find` rather than `position`**, run `check` on the live instance before it closes, or check the moves by line number after editing with Tiza closed. To fix a stale move, `delete_move` it and `add_move` it again on the code as it is now (unlike a reload, an `add_move` before other moves does carry them, see below).

## Code that changes between steps (moves)

When the lesson adds or rewrites code as it goes, do not open a second document: add a **move**. `add_move {at_step, op: insert|replace|delete, …, content, typing?, speed_ms?, rebind?}` registers a `code.patch` the TUI applies when the presenter reaches `at_step` and reverts when they go back; `render --step N` and the exports apply it instantly. Targets are matched on the code **as shown at that step** (after the moves of earlier steps and the earlier moves of the same step) and must match exactly once: `after`/`before` the text of a line or `position` (the line the content goes before; last+1 appends) for an insert; `find`, `find_start`/`find_end` or `position: "7-9"` for a replace or delete. When the text appears more than once, say which one with `occurrence: N` — 1-based, counted in reading order over the **whole** code at that step, a line holding the text twice counting twice (`end_occurrence` for `find_end`); an N past the last match is an error naming the move, and so is an ambiguous target without it. `get_code` at that step shows you the matches. `typing: "line"` or `"char"` types the content in place (`speed_ms` per unit, 120 / 25 by default).

Annotate the new code **at the step where it exists**: after `add_move {at_step: 2, …}`, an `add_note {step: 2, line: 7}` is validated on the step-2 code, whatever step the TUI is showing. Annotations of earlier steps are shifted through the patch by the patch itself (lines after an insert or delete move, a range shrinks to its surviving lines). On a line a `replace` overwrites, notes, boxes, callouts and spotlights keep the line at the same offset, but **highlights, marks and arrow ends lose their anchor** (the text under their columns is gone) and are hidden as `(unanchored)` in `list_annotations` — never deleted — unless your move names where they go: `rebind: {"a4": {"at": {"find": "t.len()", "occurrence": 1}}}` (the same fields as `update_annotation`, resolved on the code after the patch; a `find` there must match exactly once or carry `occurrence`, checked when the move is added; a spec with none of `at`, `from`/`to` or `from_line`/`to_line`, or with an unknown key, is rejected; so is an id no annotation has). An entry whose annotation goes away later (deleted, or dropped by a paste or a follow reload) is kept as written and ignored: the move applies as if it were not there, `check` warns `rebind names a4, which is not in the document; the entry is ignored`, and the entry works again when an annotation with that id comes back (`u`, or one you add with that `id`, refused when the entry would not work with it, such as a `find` that no longer matches; Tiza never gives that id to a new annotation itself). `scene.put` keeps such an entry only where the open document has it: the same code and the same move. The same goes for any annotation that loses every line. A move added after the annotations does not leave them behind: the annotations of its file **at its step or later** and the line numbers of the moves that run after it (`position`, a cursor, a `select` by line, a `code.link` window) are carried through the new patch, so they stay on the same text — insert two lines above it at step 1 and a step-3 note on line 7 moves to line 9, and lines inserted inside a later move's range (a later delete of the whole function) go with that move. `delete_move` carries them back, so deleting a move always gives back the document from before it was added. A change that cannot be undone that way is refused and says what it would lose and what to do (`annotation a4, step 3: move #8 (step 3), the one being added, removes line 15, its first line (lines 15-17); delete or move a4 first`): removing the line an annotation (or an arrow end, or the first or last line of a box, callout or spotlight) is on, rewriting the text under a mark or an arrow end (one on a rewritten line stays when the line is unchanged up to it), removing the line a later insert goes after or an end of a later move's range or window, moving a `rebind` line, or making a later move's text target match another line with the same text. There is no `move.update`: to change a later move, delete it and add it again. `delete_move` is refused the same way while an annotation is on a line that move wrote, when a later move would stop applying (a deleted `code.link` sends the later patches to another file) and when it is the only `code.link` to a file with annotations (delete them first: they would belong to no view, and the saved `.tiza` could not load them). When the move, or the deletion, leaves annotations unseen at a step where they were seen before, the reply carries a `warning` naming only those, and the change is made: outside a `code.link` window (`a3, a4: outside the window at step 3 (src/queue.rs:10-36): kept, not drawn there`), or of a file their own step no longer shows (`k2, b4, n3: their file tally/src/report.rs is not shown at step 4 (tally/src/count.rs is): kept, not drawn there`, after a link to `count.rs` at step 4, or after deleting the step-4 link when another link still shows `report.rs`); several parts are joined with `; `. Files are named the same way in the warning, in the bar's message and in `check`, live or on the saved file: a linked file by its path as the `code.link` names it, the main file as `code.file` names it (`src/stack.rs:20-30`), or by its file name when the code is embedded. `list_moves` shows every move with its index and the ids currently unanchored; `delete_move {index}` removes one. A paste is refused while a move is applied (step 0 first); a follow reload waits for step 0 (see `set_follow`).

## Showing another file (views)

To move between **files** during the demo, each with its own annotations, add a `code.link` move: `add_move {at_step: 2, action: "code.link", file: "src/queue.rs", lines: "10-36"}` shows `src/queue.rs` (a path as `code.file` would name it, relative to the `.tiza`; the TUI reads it next to the document) from step 2 on, until a later link shows another file or the main one again (`file` naming the document's own file links back; nothing else is needed). `lines` is **only a window**: it crops what is shown, every annotation keeps the file's real line numbers, and the same file with another window is the same view. A patch carries the window like any later line number (insert two lines above it at an earlier step and `17-23` becomes `19-25`), except that an insert at the window's first line **at the link's own step** grows it to start at the new lines (`17-23` → `17-24` for one line), so what that step adds is on screen (typed there with `typing`); a patch at a later step leaves the window as it is, and deleting the insert gives the window back. Annotations belong to a file: an `add_box {step: 2, …}` at a step that shows `queue.rs` is a box **of `queue.rs`** (it gets `"file": "src/queue.rs"`; you may also pass `file` to `annotation.add` yourself), it is validated on that file's code at that step, and `list_annotations` ends its line with the file in parentheses (`a4 [step 2] box L17-23 «FIFO» (src/queue.rs)`; the main file's annotations carry no suffix). While a file is shown the others' annotations are not drawn — they are not `(unanchored)`, and they come back untouched when the demo links back. A link that leaves a step showing another file than its annotations' is accepted and its reply says so (see the `warning` of `add_move`), and `check` keeps saying it (`not_shown`) until a link of that step shows their file again. Likewise a note outside the window is kept, not drawn. `get_code` returns the file shown at the current step, cropped to its window, with a first line `# src/queue.rs:10-36` naming it; `status` carries `file`, `view`, `first_line` and `last_line`. A `code.patch` edits the file shown at its step (its targets are matched there). The saved `.tiza` references the linked files by path; `:embed` (or `scene.get`, which always embeds) stores a copy of each under `views`. A link to a file that cannot be read is an error naming the move and the path.

Three small moves complete the set: `add_move {action: "cursor", line, col?}` puts the cursor on a line of the shown file, `{action: "select", from: {find: "&mut u"}, to: {find: "u);"}}` highlights from the start of the first text to the end of the second (each `find` must match exactly once at that step, or carry `occurrence`; `{line, col}` works too), and `{action: "wait", ms}` pauses before the step's annotations appear (TUI, GIF and tape; a still render ignores it). A `code.link` clears the cursor and the selection; `render --step N` draws both.

## Named steps, auto-advance and loop

**Limits** (t-166): steps run from 0 to 999 (an annotation's `step`, a move's `at_step`, a `steps` entry), a hold is at most one hour (`wait` `ms`, `speed_ms`, `auto_advance_ms`, 3,600,000 ms) and `source.first_line` at most 1,000,000,000; past them `annotation.add`/`update`, `add_move`, `scene.patch`, `scene.put` and opening a `.tiza` fail with `invalid_argument` (`move #1: step 4294967295 is past the last step a document can have (999)`), and `tiza check` reports a `bounds` error. A request that hits a bug in Tiza (a panic) answers `internal` (`annotation.add: a bug in Tiza stopped this request (a panic), and nothing of it was kept; please report it (details in …/tiza/panics.log)`): the TUI keeps running and the request is dropped whole — the document, the view, a typing animation it started and its undo entry all go back to what they were — and the panic's place goes to `panics.log` in Tiza's runtime directory; the MCP answers its own panics the same way (`internal error: the tool … call failed with a bug in Tiza …`). Tell the presenter; do not retry in a loop. `status.document` is the `.tiza` the instance saves to, once it exists on disk (what a `.tape` of the live instance opens).

A `.tiza` may name steps (t-099, ADR 0007 §4): `"steps": [{"step": 3, "id": "borrow", "title": "Shared borrow", "auto_advance_ms": 3000}]`, plus `"loop": true`. The number, not the place in the list, binds an entry to its step, so moving annotations between steps never shifts a title; entries are sparse and saved sorted by `step`; ids are unique, one word, never all digits (a number always means a step number) and never start with `-`; a bad id fails with `invalid_argument`. Only `step`, `id`, `title` and `auto_advance_ms` are known: any other key in an entry is kept but warned about in `status.warnings`. Set them with `scene.patch {"steps": [...], "loop": true}` (the whole list is replaced; `[]` clears it) or in the document you `scene.put`; `scene.get` returns them.

- `goto_step {"id": "borrow"}` (socket `step.goto`; both also take a step number, `{"id": 3}` or `{"id": "3"}`) lands on that step exactly as `next_step` would after walking from step 0: the code recomputed with every move up to it, linked files included, and a typed step complete (no animation). An unknown id fails with `not_found` and the message lists the named ones; a value that is neither (`-1`, `4.5`, `null`) is `invalid_argument` ("`id` must be a step id or a step number from 0 to N"). The reply of every `step.*` call carries `id`, `title` and `label` (`step 3/7 · Shared borrow`).
- `status` reports `step_id`, `step_title`, `step_label`, the current step's `auto_advance_ms` and `loop`; `list_annotations` starts with a `# step 3/7 · Shared borrow` line. An entry for a step past the last one is kept and listed in `status.warnings`.
- With `auto_advance_ms` the TUI goes to the next step on its own that long after the step is ready (typing finished, `wait` moves elapsed); it waits while the presenter has the `:` line, a `v`/`V` selection or an overlay open. With `loop: true`, `next_step` (and an auto-advance) past the last step is step 0. The native GIF/MP4 hold such a step for its `auto_advance_ms` instead of `--interval`.
- Scripts and editor tasks use the CLI, no JSON: `tiza next`, `tiza prev`, `tiza goto borrow` (session socket, or `--socket`/`--session`); they print the step reached and exit non-zero when no instance listens.

This is automation (recordings, a looping booth screen, an editor task), not speaker tooling: there are no presenter notes and no timer.

## Supervised mode

**Themes.** `set_theme` takes `dark`, `light`, `terminal` (the host's palette), `auto` (follow the terminal's background) or `toggle`; the reply says whether the instance is following (`auto`). A document may carry `theme_overrides` (per-token colours); `export_image` applies them and, for a terminal theme, paints the matching dark/light palette instead — there is no host palette in a file.

**The margin is the presenter's too.** `status.margin` is the cap on the right margin when one is set (`scene.patch {"margin": 24}` sets it, `null` removes it); long notes wrap at it. Keep notes short either way — a wrapped note takes rows from the lines below it.

**The gutter is the presenter's.** `status.numbers` says whether line numbers are shown; `scene.patch {"numbers": false}` hides them (saved in the document, so every export follows). Line numbers in your anchors (`line`, `find`) are the real ones whatever the gutter shows.

**One geometry per take.** `render_text` and `export_image` size the arrow lanes, the box band and the margin for the maximum over every step of the document (t-111), the same way presentation mode does: a frame at step 1 and one at step 7 put the code at the same x, so you can compare frames and build thumbnails that line up. The presenter's authoring screen may look narrower than your render at an early step; that is the dynamic layout, not a bug, and `:layout stable` on their side makes the two agree.

**Secrets on screen.** What `get_code` returns is what the audience sees, in every export and recording. If the code you read holds a real secret (a token, a password, credentials in a URL), say so to the presenter before anything is recorded and do not repeat it in a note or a label; demos should use fake values. A value outside a fixed set (a color, `border`, `corners`, `stroke`, `route`, a head, `emphasis`, `placement`, a mark `kind`, `theme`, a move's `action`/`op`/`typing`/`position`, a method name) is never repeated in an error: the message lists the valid names (`unknown border (use solid, dashed, …)`, `invalid parameters: unknown variant «…», expected one of …`). A value of the wrong type is named, so you can see what you sent (`invalid type: string "three", expected u32`; cut at 40 characters with `…`).

**What stays local.** Everything you send over the socket or the MCP stays on this machine: the `tiza` binary has no network dependencies and never opens a connection (README «What Tiza reads and writes», [ADR 0009](adr/0009-politica-de-red.md)). Your `add_note`, the code you read with `get_code`, the exports you request — none of it leaves the presenter's computer unless *they* run a separate `tiza-net` command on purpose. Do not expect a `publish` or an `upload` tool here, and do not try to reach the network on Tiza's behalf: if the presenter wants a GIF on a service, produce the file locally and tell them which command would send it.

**Saving rule.** The TUI writes every change to the `.tiza` sidecar of the file that is open — your `add_note` lands on disk at once — unless the presenter opened it with `--no-save` or turned `:autosave off` (`status.autosave` tells you; `:w` is theirs), or the sidecar cannot be written (a read-only file or folder: the presenter is told once, the bar shows `read-only • unsaved (:w)`, your calls keep succeeding in memory and `:q` refuses until they `:w PATH` or `:q!`; the next autosave that works clears it). `scene.put` of a document from **another source** (a different `source.path`, or embedded code with none) is shown but never autosaved over the file that was open: autosave stops with a message, and the presenter decides with `:w` (over the open file), `:w PATH` (elsewhere) or `:autosave on` (resume). A put of the same source — re-putting an edited copy of the open document, `scene get` → `scene put` — keeps saving as before, and **the files the open document reads stay references**: `scene.get` always hands the code out embedded (`code` and every linked file under `views`), and when what comes back is the same as that file's text **now**, the `.tiza` keeps `"code": {"file": …}` (with its `lines`) and its `code.link` paths, and only what you changed changes. It is a plain comparison of the code you send with the file on disk — nothing is remembered between your `scene.get` and your `scene.put`. Code you did change is shown but never autosaved over the file it came from: autosave stops and the bar says which file (`not saved — autosave off: the code sent for main.rs differs from the file on disk …`); to change the code itself, edit the file (or add a move). If the file changed on disk after the instance loaded it and you send back the copy `scene.get` gave you, the document still reads the file (it is never embedded in silence): the screen keeps the copy loaded and the bar says `main.rs changed on disk since it was loaded: still read from it …`. With follow on (`status.follow`) the screen shows the file as it is, so a put whose code is not the file's is refused (`the code sent is not what main.rs holds now, and follow is on …: scene.get again`) and nothing changes. A put is refused too when a file the document reads can no longer be read (`main.rs cannot be read …`). A `views` entry that no `code.link` names is ignored. A put that changes nothing writes nothing. After a put of edited code, a put of the file's own code makes it a reference again (with autosave still off, the bar says `main.rs is a reference again; autosave still off (:autosave on resumes)`). A document with embedded code (read from stdin, or frozen with `:embed`) stays embedded. `u` after a put brings the previous document back, step included. From the CLI, `tiza scene put FILE` takes a `.tiza` or the `scene get` envelope and refuses anything else unless `--as-code` is passed.

The presenter may turn on `:supervise`: then every mutating call (add, update, delete, clear, step, theme, focus, pointer, follow, scene put/patch) waits until they press `y` or `n` in the TUI. Accepted calls return their normal result (for an annotation, `visible` and `shown_step` as of the acceptance); rejected ones fail with code `rejected` ("the presenter rejected this change"), and so does a proposal left undecided for 60 s. `status` tells you (`supervised`, `pending`). Do not retry a rejected change in a loop; say what you wanted to draw and let the presenter answer. Reads never wait.

## Resources

If your client supports MCP resources, `tiza://scene`, `tiza://code`, `tiza://render` and `tiza://render.md` are always readable (no caching: every read reflects the live instance). They are the same views as `get_code` / `render_text` / `scene.get`; use whichever your client makes cheaper to attach as context.

**Control characters.** Code can hold bytes a terminal acts on (ESC, NUL, BEL…). Tiza never shows or returns them raw (t-182): `get_code`, `render_text`, every export and the `tiza://` resources show a C0 control as its picture (`␛` for ESC, `␀`, `␇`; the tab is expanded as before), DEL as `␡` and a C1 control as `�`; a bidi control (U+202A–U+202E, U+2066–U+2069, U+200E/F, U+061C) takes no cell in a drawing and is `�` in a text reply. JSON replies (`tiza://scene`, `pretty` results) keep the real characters as `\uXXXX` escapes. A `find` must use the real character (`\u001b` in JSON), not its picture. An error that quotes your `find` shows such a character in Rust escapes (`text "a\u{1b}b" not found in the code`); other errors show its picture.

## Idempotency

Pass your own `id` (`"id": "move-s"`) so that a retry does not duplicate the annotation: the second attempt fails with `duplicate_id` and you can move on.

## Finding the tools (deferred tools)

A client may defer MCP tools and load only their names and the server `instructions` at the start (Claude Code's tool search, on by default), so the instructions are written to be searched by (t-162): what Tiza is, when to use it (explain code to a person or another agent, live or recorded, step by step), the words people use for it and the flow in two lines. `status`, `get_code`, `render_text` and `add_box` carry `_meta["anthropic/alwaysLoad"]: true`, which asks such a client to load them upfront, so the first call needs no search; the others (`add_arrow`, `highlight`, `add_note`, `add_move`, `export_image`…) are found by searching for what you want to draw. A client that does not know the key ignores it and loads every tool as before; in Claude Code the person who configures the server can override it for the whole server (`alwaysLoad` in its entry).

## After a rebuild

`status` returns a `bridge` object: `version`, `build` (git commit of this MCP server) and, when the `tiza` binary on disk is newer than the running server, `binary_rebuilt: true` plus a `hint`. That means the tool list you hold may be stale: tell the user to reconnect the server (Claude Code: `/mcp` → tiza → reconnect) before relying on a tool you cannot see. `instance_build` appears when the TUI was built from a different commit than the bridge: ask the user to restart the TUI as well.

## Schema

`tiza schema document` and `tiza schema api` print the JSON Schemas (also committed under `schema/`); the live instance answers `api.schema` with the params and result of every method, so a client can validate what it sends. Agents without a terminal can pipe documents: `tiza render - --out shot.png < demo.tiza`.

## Without MCP: socket and CLI

Same contract, one JSON request per line over the Unix socket:

```sh
printf '%s\n' '{"id":1,"method":"annotation.add","params":{"type":"note","line":4,"text":"hello"}}' | nc -U "$TMPDIR/tiza/default.sock"
tiza api annotation.add '{"type":"note","line":4,"text":"hello"}'
tiza api api.methods
tiza check demo.tiza --json   # preflight of a file, no instance needed (exit 1 on errors)
```

Response: `{"id":1,"result":{...}}` or `{"id":1,"error":{"code":"text_not_found","message":"..."}}`. Codes: `out_of_range`, `not_found`, `duplicate_id`, `text_not_found`, `invalid_argument`, `invalid_json`, `unavailable`, `busy` (a `check` replaced by a newer one before it ran: ask again; t-210).
