# Document format

A `.tiza` file is a JSON document. It holds the annotations, the moves and the named steps.

New annotations appear at the current step. The `.tiza` references the source file by path (`"code": {"file": "main.rs", "lines": "12-48"}`, absolute or relative to the `.tiza`), so it always shows the current code; `:embed` freezes a copy inside the document (and a copy of every file the demo links to) and `:ref path[:A-B]` references a file again (`:link` does the same at step 0; at a step ≥ 1 it is the *move* below). Color is yours, as in Excalidraw: every annotation accepts `color` (a name or `#rrggbb`); arrows without a color rotate through a palette so they can be told apart. Arrow strokes and heads are yours too: dashed for a shared borrow, thick for a move, `heads=none,none` for a plain connector — the ownership example does exactly that. Everything is saved automatically to a `.tiza` (JSON) next to the source file (`src/main.rs.tiza`).

**Moves** (the code changes between steps, [ADR 0007](../adr/0007-moves-y-pasos-con-nombre.md)): a `.tiza` may carry `moves`, each a `code.patch` that inserts, replaces or deletes whole lines when the presenter reaches `at_step` — `n` applies it, `p` reverts it, and the document is always recomputed from the step-0 code, so going back and forth ten times leaves it exactly as it started. A target is matched on the code as shown at that step and must match exactly once (`after`/`before` a line's text or `position` for an insert; `find`, `find_start`/`find_end` or `position: "7-9"` for a replace or delete) — or say which match with `"occurrence": N`, 1-based and counted in reading order over the whole code at that step (`end_occurrence` for `find_end`). With `"typing": "line"` or `"char"` the content is typed in place (`speed_ms` per line or character; any key finishes it and is consumed — an `n` pressed mid-typing completes the step instead of advancing, so press it again; the step's annotations appear when the typing ends). Annotations are authored against the code at their own step and shifted through later patches by the patch itself — an insert or delete moves the lines after it, a box that loses an edge line shrinks — never by a text search. On a line a `replace` overwrites, a note, box, callout or spotlight keeps the line at the same offset, but a highlight, mark or arrow end has nothing under its columns any more and is hidden as `(unanchored)` in `:list` (never deleted) unless the move's `rebind` says where it goes (`"rebind": {"a4": {"at": {"find": "t.len()", "occurrence": 1}}}`, resolved on the code after the patch); the same happens to any annotation that loses every line. Adding or deleting a move later carries what comes after it — the annotations of its file at its step and later, and the line numbers of later moves — so they stay on the same text, and deleting a move gives back the document from before it; a move that would lose something on the way (the line an annotation is on, a range's first or last line, a later move's target) is refused, naming it. `tiza examples/ownership-moves.rs.tiza` shows a helper being typed in and later replaced by a method call; `render --step N`, `.cast` and `.tape` apply the moves instantly (`render --step N` past the last step warns on stderr and shows the last one; a `.tape` holds a typed step for the typing time plus half a second). A paste is refused while a move is applied (step back to 0 first), and a save in the editor waits for step 0 (follow mode, above); at step 0 a paste re-applies the moves on the new text and re-anchors every annotation on the code at its own step, so a step-3 arrow onto a line a move typed in survives; `:embed` and the saved file always keep the step-0 code.

**Several files, each with its own annotations**: a `code.link` move shows another file from its step on — `{"at_step": 2, "action": "code.link", "file": "src/queue.rs", "lines": "10-36"}`, or `:link src/queue.rs:10-36` typed at step 2 (at step 0 `:link` is the one-shot reference above; `:ref` always is). Each file is a *view*: the annotations you add while it is shown belong to it (they get a `"file"`; absent = the document's own file), their lines are the file's real line numbers, and `lines` is only a window that crops what is on screen — a note outside the window is kept and simply not drawn, the same file with another window is the same view, and linking the document's own file again brings its annotations back exactly as they were. `:list` names the file of every annotation of a linked file (`a4 [step 3] box L15-17 (src/queue.rs)`), the bar shows `↪ src/queue.rs:10-36` while a link is up, a `code.patch` edits the file shown at its step, and `:embed` stores every linked file under `views` so the demo stays one portable `.tiza` (a link to a file that cannot be read fails to load naming the move and the path). Three more moves go with it: `cursor {line, col}` puts the cursor on a line, `select {from, to}` highlights a span (each end a `find` that must match exactly once at that step, or `line`/`col`) and `wait {ms}` pauses before the step's annotations appear (the TUI, the GIF and the tape honour it; a still render ignores it). `n` applies them, `p` reverts them, `render --step N` and the exports draw the cursor and the selection at once. `tiza examples/stack-and-queue.tiza --no-save` walks a stack and a queue, back and forth, each with its own boxes and notes.

**Named steps, auto-advance and loop** ([ADR 0007](../adr/0007-moves-y-pasos-con-nombre.md) §4): automation for unattended recordings, a looping booth screen or an editor task that advances the demo — not speaker tooling (no notes, no timer, no clicker features). A `.tiza` may carry `"steps": [{"step": 3, "id": "borrow", "title": "Shared borrow", "auto_advance_ms": 3000}]`: each entry names its step by number (never by its place in the list, so moving an annotation to another step with `+`/`-` shifts nothing), entries may be sparse and are saved sorted by `step`, ids are unique, one word, not all digits (a number always means a step number) and do not start with `-` (`tiza goto -1` would read it as an option). The status line shows `step 3/7 · Shared borrow` (the id when there is no title; presentation mode has no bar, so nothing new appears in a take), `status` reports `step_id`, `step_title` and `step_label`. `:goto borrow`, the socket's `step.goto {"id": "borrow"}`, the MCP's `goto_step` and **`tiza goto borrow`** jump there exactly as `n` would after walking from step 0 — moves and linked files recomputed, a typed step landed with its text complete — and an unknown id is `not_found`. `tiza next` and `tiza prev` step the running instance, with no JSON to quote (the session's socket, or `--socket`/`--session` like `tiza api`); they print the step reached and exit non-zero with `no Tiza instance is listening…` when nothing runs. With `auto_advance_ms` the TUI moves to the next step on its own that long after the step is ready: a typed move finishes typing and a `wait` elapses first, a key meanwhile only finishes the typing, and an open `:` line, `v`/`V` selection or overlay holds the countdown until it closes. `"loop": true` makes `n` (and an auto-advance) past the last step go back to step 0. An entry for a step past the last one, and a key an entry has that Tiza does not know (a typo, the dropped `timer_min`), is kept in the file and warned about (on open, in `status.warnings`, by `render` and `tiza check`), never dropped.
